# 多窗口协同 · 谁在哪个窗口干

> **本文件讲**:**多个窗口并行时怎么不互相踩**——开窗带什么、开场怎么说、把活分给别人怎么分、交回来怎么收。
> **⚠️ v7.0 起本文件不再分配角色。** 【主线-大脑】/【主线-手】那对角色已删除,默认**当前窗口就是唯一窗口**(`SKILL.md` §3.1);碰不到的事按 `SKILL.md` §3.3 三分支处理。本文件管的是**并行时的秩序**,不是分工。
> **和 `process.md` 的分界**:那份讲**这件事怎么干**(取值 → 固化 → 展示 → 发布的过程规则),本份讲**谁在哪个窗口干**。过程规则一律在那份,本文件只指步骤号,**不重抄**。
> **性质**:索引,不是副本。同一条规则只在一处;本文件出现的都是那份没有的「开窗专用件」。
> **冲突优先级**:**用户当轮明确指令 > 工作流包 > 个人使用习惯文件**(全包统一一档,包内各文件不再分档)。

## §1 铁律与角色

**设计真值在 Figma,skill 一份、版本只签一次。** 每条版本线**只有签发方能写 skill、签版本**;分出去的其它窗口只读 + 起草,产出「待并入草案」。并行起草、合并串行(git 多分支单 main)。
> 「一份」说的是 **skill 这个执行载体只有一份、只有一个签发方**,不是说 skill 就是设计真值的源头——设计真值在 Figma(`SKILL.md` §2 总则1)。

> **⛔ 本包(WF)的版本由用户指定的单一窗口签发,当前是【工作流窗口】。** 其它窗口发现问题**只提建议、不直接改包、不自行升版**。
> **实证**:2026-09-23 出现 v6.2 与 v6.3 两条基线并存——工作流窗口按自己的线以为基线是 v6.2,而另一个窗口已签发并落地 v6.3,险些把 v6.3 静默回退。
DS skill 的版本由 DS 线的签发窗口签,两条版本线各有唯一签发方。
> 注:原文写的是「只有【主线】能写 skill、签版本」,**那是按旧角色集写死的枚举句**;v7.0 改成按**签发方**说——角色换了、载体换了都不失效(同类坑见 §8)。

**两次确认在哪儿都一样**(出处:`SKILL.md` §2 总则4):**效果确认**(数值与效果)与**文本确认**(表述与归属)都是**用户**确认,**在哪个窗口做的活就在哪个窗口确认**——不按角色分配。两次都过,才算完成。

**可能参与的各方**(都不是必须存在的角色,按需才有):

| 谁 | 典型载体 | 能写 skill 吗 | 干什么 |
|---|---|---|---|
| **本窗口** | 任意有文件能力的载体 | **能**(若它是该线签发方) | 全流程默认由它走完:取值 → 固化 → 校验 → 打包 → 签发 |
| **替你动手的 agent** | 挂了本机目录的任意模型 | ❌ 只按卡执行 | `SKILL.md` §3.3 分支③b 才出现:本窗口够不到本机时,给它任务卡 + `execution-standard.md` |
| **另开的并行窗口** | 任意 | ❌ 非签发方不写 | 分头做不同的线 / 不同的包;秩序靠本文件 §6、§8 |
| **Design / 站点** | 任意能出页面的载体 | ❌ | 照 skill 做组件、出展示站。**交回两类东西**:① **下游产物**(站点本身)→ 走对账 `process.md` §4.3;② ⭐ **它检查出的 skill 问题** → 回流改 skill。**两类常常同时出现**,判断迹象见 `SKILL.md` §2 总则2 第二层(⛔ 不套公式,判不了交用户) |

两条边界补充:

- **「另开的窗口」不限形态**——窗口、别的模型、真人同事都算;边界都是「**不是签发方就不写库、不升版**」。
- **Design / 站点就是另一个窗口,没有特殊性**(v7.2)——要它做事和别的外援一样走 `SKILL.md` §3.3 分支③;**用户也可以只用一个窗口做完 skill 再顺手做站,那时连转接件都不需要**。
  > 区别只在**交回物**:别人交回**草案**(→ 并入 skill),站点交回**下游产物**(→ 走对账)**外加 skill 的洞**(→ 回流改 skill)。

## §2 全流程里真正有约束的几步

**默认整条流程由本窗口自己走完**(五阶段见 `process.md` §3.0),所以这里不再列「哪步归谁」。下面只列**不管谁做都绕不过**的约束,细则去 `process.md` 查编号:

| 约束 | 是什么 |
|---|---|
| **操作卡步0** | 开干前先重读 skill 作准绳 |
| **待确认拍板** | 规则 / 命名 / 缺态先让用户拍板(确认前置,**不替代**两次确认) |
| **两次确认** | 效果确认(数值与效果)→ 文本确认(表述与归属);**都过了才升版打包**(总则4) |
| **🚧 硬闸门两处** | §4.6 自升级机制、§4.7 Figma 写回——**碰到牵动即停,取得用户显式同意才动** |
| **签发唯一** | 每条版本线只有一个签发窗口;非签发方**只提建议,不改包、不升版**(§1) |
| **不可逆操作** | 删除 / 覆盖 / 改名 / 推远端:先声明确切目标并取得同意(`SKILL.md` §3.3) |
| **并行撞车** | 多窗口同时动会互相踩时,见 §6;活动件互相覆盖见 §8 |

## §3 开窗:说什么、带什么

### 3.1 开场白

⛔ **开场白不是启动的必需品**(v10.0 改)。**包该靠自己被读到**——用户把包发过来、再说一句要做什么,窗口就该按 `SKILL.md` §0「零仪式启动」自己读包、自测、建载体、读真值,然后回话。

> **为什么改**:原文写的是「**没有这段,读取顺序不会被触发**」,于是整套启动押在**用户每次手打一段仪式**上。**真实场景是「把包发过去 + 说一句要做什么」**——要求用户记住一段仪式,等于把包的可用性押在用户的记性上。
> ⛔ **而且仪式里一旦写了包内的规则与术语,就等于替窗口把答案答了**:它就算一个字没读包,也能照抄那些词回话,**「它到底读没读」反而测不出来**。v9.2 新增的冷启动开场白模板正是这么写的,v10.0 已删除该模板。

**那开场白还有什么用**:只在要给**包里没有的东西**时才发——额外约束、交接上下文、本轮特有口径。**凡包里已经写了的,一个字都别写进去。**

模板**照抄,不自创**:

| 什么时候 | 模板 |
|---|---|
| ⭐ **开一个全新协作**(没有历史、参数一项未定) | **不需要开场白**——发包 + 一句工作指令即可,窗口按 `SKILL.md` §0「零仪式启动」自己走完 |
| **开一个新窗口接着做**(项目已在跑) | `assets/templates/kickoff-brain.md` |
| **把某个组件 / 某条线分给别的窗口做** | `assets/templates/kickoff-branch.md`(含**续轮任务卡**) |
| **把本地操作交给能碰本机的 agent**(§3.3 分支③b) | 不走开窗流程:给**任务卡**(`assets/templates/exec-card.md`)+ 把 `references/execution-standard.md` 整份作为常驻提示词给它 |
| **分窗口做站点** | 不发开场白,只发已定稿的参考实现文件 + 差异说明复制框(`process.md` §5.4,骨架见 `assets/templates/design-prompt.md`)。**同窗口顺手做站则什么都不用发** |

> **续轮不重发开场白**:同一个窗口做第二个及以后的组件时,只给「本轮组件 / 产出文件 / 规格位置 / 本轮特有约束」四样,**不重抄规则**——重抄一遍就是第二处副本,且两次措辞必有出入(§8)。格式见 `kickoff-branch.md` 下半。

### 3.2 带什么文件

**先判:这个窗口有没有本地访问能力?**

| 窗口类型 | 怎么拿文件 |
|---|---|
| **够得到本机**(挂了本机目录的任意载体) | 直接读工作区;开窗只告知负责哪条线 + 授权范围,不必逐份上传。授权按 `workspace.md` §二配——分出去的线只给自己那个 `drafts/{线名}/` 读写 + `skill/` 只读 |
| **无本地访问**(Claude Chat) | 用户上传,按下表打包 |

**冷启动最小清单(新协作关系;本节自给,不依赖任何包外文件)**

| | 带什么 | 为什么不能省 |
|---|---|---|
| 1 | **本工作流 skill 包** | 过程规则本体 |
| 2 | **一句工作指令**:要做什么 + 真值在哪(「做理财业务组件,Figma 链接 xxx」) | 窗口据此按 `SKILL.md` §0「零仪式启动」自己读包、自测、建载体、读真值。**不需要开场白**(v10.0 改,§3.1);要加包里没有的约束时才另附一句 |
| 3 | **被维护的那个 skill 包**——**若已存在** | 它是操作对象;真值全在那儿,本包不含任何真值。**从零建新系统时没有这一件,正常** |

⛔ **不要带上一个项目的包外活动件**(档案件 / 参数件 / 台账 / 在途件 …)。那些是**那个项目的实例数据**:带过去不只是多余,它会让 §3.0「开工问一次」问不出东西——**参数一旦预先给了,就永远测不出它该问什么**。

⛔ **也不要照搬上一个项目有几份活动件**。冷启动时三轴(频率 / 写入方 / 读取时机)大多相同,**按 `process.md` §7.0「要不要再开一份」判下来,开头通常只需一两份**;等频率与写入方分化了再拆。

**项目跑起来之后**,各角色带哪几件的细化表在**档案件**(「开窗要带什么」节),那里是权威。
> **为什么细化表在包外**(时序测试,`process.md` §7.1):用户必须在**打开本包之前**就知道要带什么。> ⚠️ **但这条不能用来推出「包里不写」**——**新协作关系没有档案件**,此时包里必须自己给得出上面那张最小清单。**v9.2 之前本节只有一句「见档案件」,于是冷启动无处可查**。
> 理由(时序测试,`process.md` §7.1):用户必须在**打开本包之前**就知道要带什么,所以那张表只能在包外。本节只管上面这条「有无本地访问」的取法差异。

> **带 zip ≠ 开窗就读全。**
> **分出去的线要瘦装时**,DS skill 侧至少给:`SKILL.md` + `assets/library-index.json` + `references/foundations.md` + `assets/design-tokens.css` + 该组件相关 `references/components.md` 段 + `assets/icons/icon-palette.html`。

### 3.3 读取顺序与按需纪律

**必读(全读,按序)**:① 本工作流的 `SKILL.md`(操作卡 + 总则 + 载体通道与三分支 + 路由表)→ ② DS skill 的 `SKILL.md` **入口**(只读版本、三层路由、硬规则,它是后面按需读取的导航)。

> **两个必读都是入口,不是全文**。本包的 `references/` 与 DS skill 的分层内容一律**触发才读**,路由见 `SKILL.md` §4。
> **用户个人使用习惯文件不在本序列**(见 §3.4):该文件(如有)由载体自动加载,**不必上传、不必列进读取顺序**。窗口若没有它,按本包执行即可。

**按需(触发才读)**:

- 做 / 核某组件 → 经 DS `SKILL.md` 路由读 `references/components.md`(通用)或 `references/scenarios/{场景}.md`(业务)**对应段** + 该组件参考实现
- 用图标 / token / 资产 → 查 `library-index.json` 定位确切引用,再读那个文件
- 对账 / 发布 → 才读设计站**相关页**(先核版本戳,`process.md` §4.3)
- 配授权 / 归档整理 → 才读 `workspace.md`
- 这轮只碰行情,就不读交易 / 理财场景段

> **按需读取不是偷懒,是纪律**:省的是用不上的预读;真用到的段必须经 `SKILL.md` / `library-index` 定位读准(守总则1),**不靠记忆脑补**。
> ⛔ **「触发才读」= 触发的那一刻读。** 开工时预读过的,**动手前照样要回去重读那一节**——隔了十几轮只剩模糊印象,那和没读一样,**还多了一层「我读过了」的错觉**。判据与实测在 `process.md` §7.0。

| **验证反馈件** | **任何验证方**照 skill 亲手做东西时撞出的 **skill 待修项**(总则2 第二层情况2那一类):站点验证、还原设计稿、别的窗口照 skill 产出,**按来源分节放同一份** | 🔻 做验证时 / 批量修 skill 时 |

> ¹ 🏷️ **实例层**:站点与发布仓的具体地址是 `{站点}` / `{发布仓}`,真值在项目侧参数件(`SKILL.md` §3.0)。口径:「下载 Skill 包」按钮**指向发布仓**;站内那份 zip 保留,作**自升级备用源**(`process.md` §4.6)。

> **包外活动件怎么命名**:`{层}{使用场景}-{书名}_{版本}.md`。
> **层** = **通用**(跨项目,可直接搬走)/ **国金DS**(本项目专有)。
> **使用场景** = **常驻**(每窗口都要,按需读不预读)/ **按需**(触发才带)。
> **版本**:活动件的**文件名可以带版本号**,只用来分辨手上是哪一份,每改一次升一位。**引用一律写书名、不写版本号、也不写路径**——文件名每升一位路径就变,写死路径必失配。详见 `process.md` §7.0。
> **序号**:同一「使用场景」下有多份时才加(`按需1` / `按需2`),**只剩一份就不加**——序号的用处是排读取顺序,只有一份时它只会误导。
> **为什么要有**:挑文件时只看得到文件名、看不到任何表格;标签把「哪一层 / 什么时候用」写进文件名本身。
> ⚠️ **改名会改变文件名主干**,触发执行端 §八「主干相同、仅版本号不同」判据失效——归档时须在任务卡里点名两个确切文件、写明出卡方裁决,不走机械匹配。

## §4 窗口按线开,弃挂窗即重启

事实源在文件里、不在对话里。窗口卡死 → 弃掉,用 §3 冷启动重开接力,**损失为零**。

**一条线一个窗口,不按组件开窗**:分出去的线按**线**划分(通用 / 理财 / …),该线的组件在同一窗口内**逐个串做**,做完一个接下一个。开窗成本是重读 `SKILL.md` + 本文件 + DS `SKILL.md` 入口,按组件开窗等于每个组件重付一次,属纯浪费。

**什么时候才弃窗**:① 窗口卡死 / 上下文溢出;② 该线的批次整体完结;③ 窗口已被前几轮的错误上下文污染、纠偏成本高于重开。**不因「做完一个组件」退役。**

> 签发窗口同理:1 个窗口按线长期沿用,不因做完一件事就弃。

## §5 交付包 —— **出方交什么 · 收方怎么验**

> **触发:凡一份做好的组件材料要从一个窗口交到另一个窗口入库——两个方向都算。**
> - **你是出方**(本窗口只出素材、不签发;`SKILL.md` §3.0 第6项第三形态)→ 读「**出方交什么**」,按七项填 `交付说明.md`;
> - **你是收方**(把某个组件 / 某条线分给了别的窗口;§3.1 表里「另开的并行窗口」那行)→ 读「**收方怎么验**」。
>
> **只有流程由本窗口自己从头走到签发时,才不需要本节。**
>
> 🔴 **本节从前叫「别的窗口交回来的东西」,整节是收方口吻,于是出方从不认领自己。**
> **实测(2026-11-09 发生、11-10 由检查窗口逐项比出)**:做业务组件的窗口被用户明确告知「只产出素材、不能自己升级 skill 包」,它**照样没用本节、没用模板**,自己发明了一套 `spec.md` + 入库说明;
> 事后检查窗口逐项比对,**缺的正好是这七项里的四项**——直读真值清单 / 效果确认凭证的原话 / 裁决点清单 / 未完成同步清单。
> **规则一个字都不缺,缺的是「这条写给谁」。** 通则见 **§8 第五问**。

对偶于 §3.2「带什么文件」——那是开窗时给对方的,这是做完之后交出来的。**给齐七项,收方才验得动;缺项退回重补,白费一轮。** 填写骨架见 `assets/templates/handoff-package.md`。

### 出方交什么(七项)

1. **组件标识**:全限定名(提案)+ Figma node-id + 文件 key + **归属提案**(≥2 场景 → 通用、单一 → 业务、拿不准标问;出处 `SKILL.md` §2 总则7)。
2. **效果确认凭证**:用户确认原话 + **参考实现源 HTML**(去批注即可转参考实现;须 `check-page.py` 0 P0 + 渲染眼检过;`process.md` §4.8 闸B / §5.2)。
3. **直读真值清单**:每个数值 / 颜色给【**变量绑定名 + 解析 hex**】两者;读不到标 ⚠️ 不推导;**绑定名与 hex 不一致时显式标出、不替收方拍 token 名**(语义 token 按用途由收方定:图标 CI / 文本 CT / 涨跌 CS;`process.md` §4.1#1-2)。
4. **构成与嵌套**(复合组件必给):列出内部可复用原子,逐个声明「建议独立成组件 / 折进组合」,指出是否复用既有组件;**不得把可复用原子写死折进组合**(`process.md` §5.1)。
5. **多版草案全带**:同一组件有多版确认草案(如固定宽 vs 自适应)时全带 + 标哪版为准;说明本批交哪些、其余挂哪。
6. **裁决点清单**:凡覆盖直读、用户拍板、缺态补全、命名 / 归属提案,逐条列「🚧 请收方复核 + 依据」(`SKILL.md` §2 总则4)。**散在「备注」里不算列。**
   > ⭐ **最容易漏的一类:被维护 skill 的推导规则与 Figma 实测值对不上。**
   > ⛔ **这件事 `SKILL.md` 总则1 已经裁断过,不是让你择一边**:**Figma 的实测值是真值**;skill 那条推导规则跟它对不上,**那是 skill 的洞**,按总则2 第二层情况2 回流(落点:验证反馈件)。
   > **所以你要做两件事,不是一件**:**① 按实测值做**;**② 把这处冲突列成裁决点**——写明「稿内是 X · skill 规则推出 Y · 我按 X 做了 · 请复核这条规则」。
   > **实测(2026-11-09 做、11-10 查出)**:运营位高度 Figma 是 **128**,窗口按 DS 的「行高 = 字号 × 1.5」改成 **130**。**按总则1 它改反了**(Figma 才是真值),**而且没列出来**,签发方无从复核。DS 那条规则本身也有歧义(入口写得像红线、`foundations.md` 写「设计建议,不是硬性规定」),已回流 DS 线。
   > ⭐ **另一类:命名提案背后的结构假设。** 同一实测里「输入区-默认 / 错误 / 转出」被当成一个组件的三个变体来命名,**而它们在 Figma 里是三个独立组件**——这种提案要**连假设一起写明**。
7. **未完成同步清单**:待收方做的(写库 / 升版 / Design / 对账 / 发布)分类列出。

⛔ **出方不得在交付里给收方下「与被维护 skill 冲突」的指令。** 七项里只有**待办**和**提案**,**没有「规则」**——你觉得收方应该照某种写法做,那是**裁决点(第6项)**,不是入库说明。
> **实测(2026-11-09 写、11-10 查出)**:入库说明写「给嵌套在内部的 C24 / C01 补 Figma 编码」,而 DS 规则是**只标组件最外层、嵌在里面的不另标**。**签发方照做就是违规。**

**交回位置**:够得到本机的写进 `drafts/{线名}/{组件编号}-{组件名}_{日期}/`;够不到的由用户上传给收方窗口。

### 收方怎么验(收到之后、写库之前)

⛔ **七项齐不等于内容对。** 齐不齐是**形式检**;下面五条是**内容检**,**都过了才写库**:

| # | 验什么 | 怎么验 |
|---|---|---|
| 1 | **形式** | 七项逐项在不在、有没有写「略」。缺了就**退回重补,不替它补** |
| 2 | **参考实现** | 用**被维护 skill 当前版**的检查脚本重跑。口径照 `process.md` §4.8 **闸门 B:P0 = 0 才准入库**;跑出来与对方自报**对不上的,逐条查为什么**(多半是它用的版本旧了);剩下的 P1 逐条判是不是可忽略 |
| 3 | **数值** | ⛔ **自己直读一次 Figma 抽查**,别只看它给的清单——高度 / 边距 / 间距 / 字号 / 颜色各抽几项 |
| 4 | **复用与色值** | 它摘进来的既有组件样式,与**库内现行值逐字比**(浅色、深色都比);少带了哪几个变量要记下来 |
| 5 | **渲染** | 每个变体渲染出来自己看。**逐项比对哪些项照 `process.md` §6 自检5,这儿不重复**;**本条的增量是「与 Figma 截图逐块对」**(不是只看渲染得对不对,是和稿对)。字体按 §5.2 硬规则,**降级必须显形** |

> **验完给三种结论,可以同时成立**:**可入库** / **内容要先改(列清哪几处)** / **形式要先补(列清缺哪几项)**。
> ⛔ **「内容基本过关」不等于「可以入库」** —— 这两句要分开说,否则出方会以为过了。
> **实证 2026-11-10**:检查窗口正是按这五条核出「两个组件内容基本过关,但交付形式缺四项、内容还有 3 处要先改」。**这套方法是它现场摸出来的,v11.0 照它固化。**

## §8 防漂移

### 写规则时最常犯的五种:祈使句少限定、触发条件写窄、视角写成单边

⛔ **包里每写一条「必须 / 不要 / ⛔」、每给一节写「触发:…」,落笔前问五句**——答不上来的那一句,就是你正在写死的地方:

| 问 | 答不上来会怎样 | 实证 |
|---|---|---|
| **它什么时候不成立?** | 写成绝对禁令,读者判不了何时安全;还会和别处的「必做」自相矛盾 | v9.2 写「不要跑自升级自检」,**没写条件**——真正的条件是「仓里那份比你手上新」;用户当场证伪(仓 6.12 < 手上 9.4,脚本静默退出)。v9.3 刚因同类问题修过一次 |
| **改的 / 做的是哪一份?** | 作用对象没写,读者会作用到错的那份上 | v9.2 写「把那三行默认值改成接手方的」,**没写改的是交出去那一份副本**——**规则落地当天就被它自己的作者读错一次**,差点去改本地那份、把自己的自升级弄断 |
| **这句话是不是包里已经有了?** | 写进开场白 / 任务卡 / 交付里就是第二处副本,**而且等于替对方把答案答了** | v9.2 的冷启动开场白模板把 §3.0 / §3.3 / 三轴 / 实例层全抄了进去,**窗口没读包也能照抄那些词回话**;v10.0 已删该模板 |
| **这一节的触发条件,会不会把同类活动排除在外?** | 条件写窄 → 读者判「本节不适用」→ **整节条款一起失效**,比漏一句严重得多 | v10.0 `process.md` §4.7 触发条件只写「把已固化真值**反向建 / 改** Figma 组件」,窗口做的是「从设计稿复制再改成组件」,**判定不适用**,于是整节的变量绑定一条没做(2026-11-09 冷启动实测) |
| **这一节是写给谁看的?另一边的人认得出自己吗?** | 视角写成单边,**另一边整节不认领**——比条件写窄更隐蔽,因为条款一条都不少,只是没人觉得是在说自己 | v10.1 §5 整节是收方口吻(标题叫「别的窗口交回来的东西」、正文说「收方即可直接写库」),于是**出方从不认领**:做素材的窗口被明确告知「只出素材」,仍没用本节与模板,缺了七项里的四项(2026-11-09 检查窗口逐项比出) |

> **五条是同一个毛病的五面**:**把话说死、说满、说到对方那边去、把管的范围说窄、把视角写成单边**。
> **验法**:写完回头读一遍,**凡出现「一律」「绝不」「必须」「不要」,就在旁边补一句「除非 / 仅当」**;补不出来,多半这条本来就不该写成禁令。
> **第四问另有一个验法**:**凡写了「触发:…」的章节标题,问一句「同类的活动还有哪几种?」——全列进去,别只写最典型那一种。**
> **第五问的验法**:**凡一节讲的是两方之间的事(交接、转交、分派、验收),把标题和首句念一遍,问「出方读到这儿会认领吗?收方呢?」**——有一边不认领,就改成双视角,或者干脆拆成两节、各写各的。

- 本文件是**分工映射 + 开窗专用件**,不放过程规则。改规则去改 `process.md`,不改这里。
- **别再派生新文件装规则**:新规则按归属进用户个人使用习惯文件(通用,如有)、`process.md`(项目过程)或 `execution-standard.md`(执行纪律)。**通用层若不在本项目掌控内(如挂载 skill),规则仍按项目层就近收进 `process.md`,不为它派生新文件。**
- **同一条规则只写一处**:并入前的《主线支线分工卡》与《协同文件包开窗指引》都栽过——分工卡 v1.0 重抄工作流正文成了第二处副本,分工卡与开窗指引又各存一套开场白。**发现某条在两处都写,就该合并或改成指向。**
- **模板只存 `assets/templates/` 一处**:正文引用模板一律给路径,不在正文里再抄一遍(例外:`execution-standard.md` 要单独 cp 给执行端,其反馈模板必须内嵌自包含,见该文件 §五)。
- **对外分发**:直接打包本 skill 包,按对象手动删不该给的——**给同事时删档案件**(含待办、踩坑、否决,对外无意义且暴露内部判断);只要执行端纪律的,给 `references/execution-standard.md` 一份即可。**不另立分发清单**(同一份文件存两处必漂移)。
- **⚠️ 拆条 / 改标题时,先把限定词单独摘出来**:「全员」「一律」「所有」「凡…」看着像修饰语,实际是**这条规则管多宽的唯一依据**。删掉不报错、不冲突,只会让某个角色以为「这条不管我」。
  > **验法**:拆完问一句「**谁必须守这条?**」——答不上来就是限定词丢了。
  > 实证:合包时一次丢了三条(总则3.2「贯穿全员」· 总则6「凡转交给 Design/trae」未扩到主线-手 · 总则7「全员引用组件时遵守」),规则内容都在,适用范围全没了。详见 `CHANGELOG.md` v6.1 §3。
- **⚠️ 把一条规则下沉 / 移交给别的载体时,先在接手方逐句找到承接位置,再删原条。** 只确认「对方有相关章节」**不算**——要指出**承接的是哪一句**;承接不了的那部分,**原条不许删**。
  > **验法**:删完问一句「**这条规则现在写在哪?**」——答不出确切位置,就是没接住。
  > 实证:个人习惯 v4.5 把「视觉交付」以「预设项目有视觉产出」为由下沉到项目层,WF 只接住了「效果确认出校验图」这一半,**「说明要配图」那一半两边都没有了**,隔一个月、连着四个组件用户看不懂才被发现(规则已补在 `SKILL.md` §2 总则4)。
  > 同族于下面两条:**都是重构时内容掉在地上**,区别只在掉的是限定词、是枚举句,还是整条规则。
- **⚠️ 动手改包之前,先重读包外活动件**——至少**校验台账**的**攒批区**与各**口径节**。基线可能在你上一轮之后被别的窗口改了,而**你手上的包和记忆都不会告诉你**。
  > **验法**:开工第一件事问「**上次我动它之后,有没有人改过口径或加过建议?**」——答案只能从活动件里读,不能从记忆里取。
  > 实证(工作流窗口,两天两次):① 10-27 建 v6.10,按 10-26 旧口径写了 7 处反话,用户 10-27 已改口径,**整包从上一版重做**;② 10-28 建 v6.11,另一个窗口当天写进台账的建议没赶上(这次不疼,只因它本来就该攒批)。
  > 与下面两条同族:**都是「别人改了我不知道」**,区别在那两条管包内条文,这条管包外活动件。
- **⚠️ 活动件只能整篇写回,后写的会覆盖先写的——而且双方都收不到任何提示。** Project 文档**没有逐条补丁**:只能整篇读出来、改、整篇写回。A 窗口读了一份,B 窗口在这期间改完写回,A 窗口再写回,**B 的改动就被整篇盖掉**。
  > **三条防法**:① **要写的那一刻再重读一次**(不是开工时读的那份),改动面越小越好;② **只加不删**——往别人的区块里追加,不重排、不整理、不「顺手清理」看起来过期的条目;③ **写完复读一次自己刚写的那几处**。
  > ⭐ **v8.1 更正**:**载体现在会挡住「基于过期版本的整篇写回」**(2026-11-06 实测,被拒并提示重新读取)——所以上面那句「双方都收不到任何提示」只对**另两种撞法**成立。**三条防法一条都不撤**,哪条防哪种撞法见 `process.md` §7.0「载体的并发能力实测」,此处不重抄。
  > 实证(2026-11-04 → 05):工作流窗口往**校验台账**写的四处(站点回退发现、发布面结构、两条口径变更、两条攒批建议)次日读回**全部不在了**,只剩改动前那一句;另一份文档里还留着「原本那里的 **1 条**已搬过去」——而当时是 3 条。**是靠复读发现的。**
  > 与上一条互为反面:上一条是「**别人改了我不知道**」,这条是「**我改了别人不知道,而且我的改动已经没了**」。丢的不是信息,是**已经核实过的结论**。
  > **第二条实证(独立发现)**:**验证反馈件**第 3 条写着「此前**校验台账**曾记过同一条(首页还原测试发现),**现台账里已不见**
- **⚠️ 改任何一处规则,先问「同族的还有哪几处」,改完回扫。** 这是本项目**重复最多的一个毛病,到 v11.0 为止已经十次**,而且每次都不报错。
  > **三类同族句,照这个顺序扫**:
  > ① **按旧角色集写死的枚举句**(「发给 X 的…」「X 负责…」)——新增角色 / 通道 / 载体时必扫,不扫就**让新角色在规则里查无此条**;
  > ② **跨处的交叉声明**(「(X 已写)」「见 X」「出处 X」)——改 X 时必扫,不扫就**留下一句指向已经不存在的说法**;
  > ③ ⭐ **同一张表下面的「收尾 / 回话 / 结论」格子**——**往表里加了一行,就把这些格子念一遍**,它们多半是按原来那几行写的。
  > **验法**:改完问一句「**这条规则的反面 / 下一步 / 另一半写在哪?那儿要不要跟着改?**」
  > **实证(只列最近三次)**:v10.0 改了 §0 的自升级口径、**漏了 `process.md` §4.6**,那儿还声称「操作卡已写」,指向一个已经不存在的说法(v10.1 修);v10.0 在 §3.0 加了「默认 1 份载体」、**没回扫同一节里的「参数件默认分开」**(v10.1 修);**v11.0 给 §0 入口表加了「整页 / 整稿」一行、没回扫同一张卡下面的「回话」格**——那格还写着「建议从哪一个开始」,**而那时候连有哪些组件都还不知道**(v11.1 修)。

## §9 轮次编号制(原 `SKILL.md` §3.2,v9.0 搬来)

凡有下游执行者的任务,**每轮签发一个唯一编号**,下游一切产出物(执行反馈、草案、交付件)的文件名与标题都带该编号。

#### 编号格式

```
EXEC-{窗口码}-{三位序号}          例:EXEC-WF-001、EXEC-DS-014
```

- **窗口码绑「任务域」,不绑「窗口实例」。** 窗口卡死重开、换人接手,码不变、序列接着走(`multi-window.md` §4 窗口可弃)。
- **每个任务域一条独立序列,各自从 `001` 起。** 域与域之间**不共享计数器**——共享计数器要「读—改—写」,两个窗口同轮各读到同一个值就都会用它,**撞号是必然不是偶然**。
- **码的分配与各域当前最大号登记在「档案件」的「窗口码登记表」**。那是**登记表不是锁**:即使某窗口记错,错也只在本域内,且一眼可见。

> **⛔ 为什么不用共享计数器**:v6.4 试过「下一个可用编号记在**档案件**」,**在多窗口下不成立**——各窗口拿到的**档案件**是用户当轮上传的快照,彼此看不见对方的写入。**结构上不可能相撞,才叫防撞;靠协调不撞,只是还没撞。**

#### 三条配套

- **编号与载体无关**:正式任务卡是它,直接贴一行短清单也是它,共用本域那条序列。**不设「短任务免编号」的例外**——一有例外,下游就得先判断再选格式,那个判断点就是下次出错的地方。
- **漏发编号是出卡方的失误**:下游标 ⚠️ 报回并沿用上轮编号加 `-b`,**不因此降级输出形态**。
- **收卡端撞号即拒收**:编号与已执行过的某轮重复时,执行端停下报回、不执行(`execution-standard.md` §九)。**这是最后一道网**——只有执行端同时见过所有窗口的卡。

#### 文件名

`{编号}-{任务摘要}.md`,例 `EXEC-WF-001-land-v6-5.md`。

- **摘要必须含「对象」,不能只有通用动词。** ❌ `land-package` / `update-doc`(哪个包?哪份文档?)✅ `land-v6-5` / `fix-listheader-p1`。**不同窗口的通用动词必然重名**,而编号已经防住了撞号,摘要要防的是**人眼认错**。
- **⛔ 文件名里不写版本号之外的版本信息**——版本号写进卡的正文;摘要里那个 `v6-5` 是**对象名的一部分**,指的是「哪件东西」,不是「本卡属于哪版规则」。
- 任务卡不进工作区、不打包上传,**不受总则3.3 的 ASCII 命名约束**。
- **📝 曾用名**:v8.1 起**统一叫「任务卡」**,v8.1 之前包里「任务卡」与「任务卡」两个词并存(41 : 29),指的是同一件东西。`CHANGELOG.md` 与模板文件名 `assets/templates/exec-card.md` 保留旧写法,**不因改名动文件路径**(动了所有引用都要跟着改,收益为零)。
- **编号在 present 那一刻才取,起草时不占号。** 实证:`EXEC-DS-002` 作废、`003` / `004` 未发即废——**五个号里三个空转**。
- **下游产出物的命名**以其常驻规范为准(`execution-standard.md` §五),本处不重抄。
