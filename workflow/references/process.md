### 总则3.3-细则 · skill 包打包合规

承 `SKILL.md` §2 总则3.3 的三条硬约束,打包时另守:

- **顶层目录名 + zip 文件名带版本号**,用 **ASCII 下划线、不用点号**(如 `guojin-securities-design_v3_19_1/` 与同名 `.zip`),解压后从目录名即可溯源。`validate.py` 已加「目录名缺版本」**P1** 提醒。
- **中文或点号目录名会被拒收**——实例:旧 `国金证券客户端设计系统-skill_v3.17.1/` 不可传,改 `guojin-securities-design/`。
- 打包**排除** `__MACOSX/`、`*.DS_Store`。
- **🚧 打包前必跑:版本号四处一致断言**(总则3.3 条2 要求三处一致,CHANGELOG 最新条目是第四处)。**眼看过不算**——本包 v7.0–v8.0 连续六版的 `metadata.version` 与标题停在 `6.12`,都是眼看过的。
  ```bash
  # 在包顶层目录内执行
  V=$(cat VERSION); M=$(grep -m1 '^  version:' SKILL.md | sed 's/.*version: *//')
  T=$(grep -m1 '^# ' SKILL.md | grep -o 'v[0-9.]*$' | tr -d v)
  C=$(grep -m1 '^## v' CHANGELOG.md | sed 's/^## v//;s/ .*//')
  [ "$V" = "$M" ] && [ "$V" = "$T" ] && [ "$V" = "$C" ] && echo "OK $V" || echo "X 不一致: VERSION=$V metadata=$M 标题=$T CHANGELOG=$C"
  ```
  > **漏网原因**:自升级与 `check-update.sh` **只核 `VERSION` 文件**,没有任何一步去核另外几处。**有副本就必须有断言,否则副本一定漂。**
- 校验:`validate.py` 已加「非 ASCII 文件名 / 目录名 = **P0**」守卫,产出前自动拦截;版本一致性改读 `VERSION` 文件。
- **本规范不影响自升级**:`check-update.sh` 首选认发布仓里的固定子目录(`design-system/` / `workflow/`)、核其中 `SKILL.md` 与 `VERSION`,**不依赖本地包目录名**;站点备用源那条才按 zip **文件名**取版本——**所以站内 zip 的包名前缀不能改**(见 §4.6)。
- **🚧 包内可执行脚本,升版时至少跑一次冒烟测试**,且**要在缺少可选依赖的环境里各跑一遍**(如有 / 没有 `rsync`)。实证:DS `check-update.sh` 的 `cp -rf` 回退分支有两个真缺陷(不删文件、写坏正在运行的自己),从 v3.x 活到 v4.1.1 都没被发现——**有 rsync 的机器上这两个 bug 根本不出现**,只跑「正常路径」测不出来。

### 总则3.5 · 站点(展示站)版本号

> 🏷️ **本节属项目实例层**(见 `SKILL.md` §3.0「包分两层」):里面的具体值按本项目写,**换项目整节替换**;通用的是「要有这么一节」。

站点版本 = **展示站自身独立 semver**,与 DS skill 版本**解耦**、不要求相等(延续「设计系统与工作流版本号各自独立签发」)。

1. **升位 主.次.修**:破坏性改版 / 整站重构 → 主;新增页面或区块、内嵌 skill 包升到新大版本、成规模内容同步 → 次;文案 / 单值 / 局部小修 → 修。
2. **站点各页 / 区块「反映哪个 skill 版本」由【页面内每块版本戳】承载**,**不靠站点版本号表达**——故站点可处 patchwork(不同区块戳不同 skill 版本);**所有区块对齐到某 skill 版本后,方可在文案 / 对账中称「站点已整体对齐 DS vX.Y.Z」**。
3. 站点包内置 `SITE-CHANGELOG.md` 为站点变更**唯一记录**(格式同 skill CHANGELOG);folder 名 + zip 名带站点版本(纯 ASCII,如 `guojin-ds-site-v3_18_0`)。
4. **边界**(延续「展示层只动表现、不反向改真值」):skill 升版**不强制**站点升版(展示层按需同步,同步即按上述升位 + 写 SITE-CHANGELOG);站点升版**绝不反向改 skill 真值**,内嵌 skill 包永远取 skill 已签发版本、不在站点侧二次编辑。
   > **站内那份 zip 现在有两个身份**:既是站上的下载备份,也是**自升级的备用源**(§4.6)。**每次发版由用户本人同步到当版**——不出任务卡、不归 Design 窗口(用户 2026-10-27 定)。
5. **更新与止乱(版本权威 · 防倒挂 · 验回退 · 正名)**:
   - 站点版本号**唯一权威 = `SITE-CHANGELOG.md` 最新条目**;**Design 重生成站点时的 folder 名 / 页眉徽标一律不作版本权威**(Design 常把 folder 标回旧值,如把 v3.19.3+ 内容标成 v3.17.1)——维护方打包时以 SITE-CHANGELOG 为准重标 folder / zip 名。
   - 新版本号**必须 ≥ 现 SITE-CHANGELOG 最新版本**、从「用户保有的真实最新」往后接续,**严禁拿 Design 重生成输出的(可能被标回旧值的)folder 名当基准 +1**(否则「新包版本号 < 已有版本号」倒挂)。
   - Design 从源重生成后,维护方打包前**先与上一基线逐文件比对**(diff 分类:本轮同步项 vs ★其它),确认除本轮同步项外**无内容回退**方可续版;有回退则以基线为准重做。
   - Design 输出 folder / 徽标与真实内容版本不符时,以真实内容续接版本线、在 SITE-CHANGELOG 记「正名」,**不沿用误标**。

### 总则3.6 · 可视化站部署交付规范

> 🏷️ **本节属项目实例层**(见 `SKILL.md` §3.0「包分两层」):里面的具体值按本项目写,**换项目整节替换**;通用的是「要有这么一节」。

Design 交付可上线的部署夹时,以下为**唯一权威**;§4.5 的操作步骤直接引用本节,不重述。

1. **页面文件名一律 ASCII**:首页=`index.html`、基础规范=`foundation.html`、通用组件=`components.html`、业务场景=`scenarios.html`、指南=`tutorial.html`。
2. **`index.html` 在最外层。**
3. **链接全量同步**:首页卡 / nav-data / 面包屑 / ⌘K / 页间互链,旧名改新名,**交付前 grep 零残留**。**「下载 Skill 包」按钮指向 GitHub 发布仓**(§4.6),不参与 ASCII 改名;但站内那份 skill zip 仍在 `assets/`,**它的链接必须留在 `index.html` 里**——自升级的备用源靠解析它取版本(§4.6)。
4. **`assets/` 资源也 ASCII**(如 `guojin-ds-skill-v5.0.0.zip`)。⛔ **站内 skill zip 的包名前缀不可改**(`guojin-ds-skill-`),版本号在文件名里——自升级备用源按这个式样解析(§4.6);页面里**只留一个版本的链接**,脚本取第一个。
5. **🚧 红线**:部署层**只动文件名与链接**;页面渲染 / 交互、token 数值、750 示例、壳层逻辑**一律不变**。
6. **维护方机械注入时同样守此规范。**

## §3 主流程:标准循环(每个组件 / 每个维度一轮)

### 3.0 五阶段鸟瞰(原 `SKILL.md` §3.4,v9.0 并来)

> **和下面那张九步循环是同一件事的两种粒度**:本节按**阶段**看(一个组件从想法到线上经过哪五段),下面按**步**看(一轮里依次做什么)。v9.0 之前两份分别放在 `SKILL.md` 与本份,**两处措辞已开始分叉**,故合并到一处。
从一个组件的「想法」到「线上可访问」,五个阶段:
```
① 构思/取值  —— Chat 经 Figma MCP 直读节点真值与变量绑定(§4.1);源规范不全则 Chat 完善(§4.2)
       │            产物:已读到/⚠️待确认清单 + 命名提案(用户拍板)
② 固化      —— Chat 裁决赋义 → 效果确认过 → 写进 skill(md/css)→ 文本确认过 → Code 校验/打包/升版本
       │            产物:效果确认校验图 → 确认后 DS skill(多文件路由 zip;单文件基础规范按需)
③ 展示      —— 用户把「只含定稿差异」的提示词/参考实现文件给 Design → Design 更新可视化站(§5.4)
       │            产物:多页自包含可视化站(每页内联、离线可预览)
④ 对账取证  —— Design 导出回传 → Chat 先核版本戳 → Code diff + Figma 直读逐项核验(§4.3)→ 偏差回 Design 修
       │            产物:取证通过的可视化站
⑤ 发布/部署 —— 整理 ASCII 文件名部署包(index.html 在最外层 + 英文页 + assets/,含站内 skill zip)→ 上线(§4.5)
                    产物:线上站点;「下载 Skill 包」指向 GitHub 发布仓,站内 zip 作自升级备用源(§4.6)
```
铁律贯穿:**设计真值在 Figma、skill 是固化而来的执行载体**(总则1);差异**分两层裁决**——Figma ↔ skill 以 Figma 为准;skill ↔ 站**双向**:可能改站、也可能是站检查出了 skill 的问题而改 skill,**逐条判、不套公式**(总则2);版本号全员贯穿(总则3);用户确认才算完成(总则4)。**展示 / 发布层只动表现与文件名,绝不反向改真值。**
> 上表 §4.x / §5.4 均指 `references/process.md`。**总则3.5(站点版本号)与总则3.6(部署交付规范)的正文也在那份**(`process.md` 开头的「总则3 · 下沉细则」节)——它们叫「总则」但不在本页,**查不到别当没有**。


```
① 用户:发 Figma 节点链接给 Chat(主路径;截图仅作视觉补充或 MCP 不可用时备用)
② Chat:经 Figma MCP 直读真值与变量绑定(4.1)→ 输出前自检(见 §6)→ 列「已读到 / ⚠️待确认」
       ├─ 有待确认 → 用户拍板规则/命名,不出**校验图**(确认前置,非正式确认)
       │              ⚠️ 但**待确认项恰恰最需要说明图**——Figma 疑点、方案取舍、要指位置的,
       │                 配截图 / 标注 / 对比(`SKILL.md` §2 总则4)。省的是渲染,不是沟通。
       └─ 无待确认 → 进 ③
③ 【效果确认】渲染校验图(默认 inline 可视化;需留档/离线则出自包含 HTML)→ 用户确认「数值与效果」→ 反复改到"对了"
       └─ 效果确认未过 → 不写进 skill
④ 写 skill:按标准结构重写表述(5.3)写进 skill(md/css)→ 反推自检(自检6)
⑤ 【文本确认】把固化文本给用户抽查「表述与归属」→ 过了才进 ⑥
⑥ 打包/升版本:Code 校验 + 打包 skill(单文件基础规范按需)+ CHANGELOG 升版本 + 回写看板 ✅(文本确认未过不得做本步)
⑦ 同步:Chat 出「只含定稿差异」的 Design 提示词(能给参考实现文件就给文件,5.4)→ 用户粘/传给 Design → Design 更新可视化站
⑧ 取证:Design 导出回传 → Chat 先核版本戳 → 对账取证(4.3)→ 偏差回修
⑨ 发布:站点成熟后整理部署包上线(4.5);日常迭代回到 ①
```

- **校验图交付形态**:默认 **inline 可视化(widget)** 做日常快速校验;**需留档 / 离线 / 像素级自检时,产出自包含可下载 HTML**。两种都要求自包含、可交互、用真实数值。
- **取值路径**:默认走 4.1(Chat Figma MCP 直读);直读未覆盖处(如 SVG 内封装值)标 ⚠️,需要时辅以截图对照;源规范本身不完整则插入 4.2。
- **两次确认**:见 `SKILL.md` §2 总则4——效果确认过才写 skill;文本确认过才打包 / 升版本 / 回写看板 ✅。待确认拍板是确认前置,不替代两次确认。

## §4 子流程(按触发条件插入主流程)

### 4.1 样式提取(Chat 经 Figma MCP 直读;触发:需要 Figma 真实数值)

**用 Figma MCP 之前,先把该载体的 Figma skill 读了。** 多数载体把 Figma 的用法放在一个单独的 skill 里(常见名 `figma-use` / `figma-design-to-code` 一类),**不读就调,常见的失败是参数形态不对、或该先建 session 没建**。**本节只管「取到的值怎么用」,不重抄某个载体的调用方式**——那随载体变,归载体自己的 skill。

**⚠️ 导出图片有返回值上限。** 实测 `exportAsync` 单次返回上限约 **48KB**,超了直接失败。两条绕法:**① 分批导出**(按节点拆、或降分辨率);**② 从会话记录里把 base64 取出来再解码**。**别把失败当成「这张图导不出来」**——先判是不是撞了上限。
> 这类**工具上限**与具体设计系统无关,所以归本包;而「某个组件的编码去哪查」「某份参考实现的样式怎么摘」**依赖 DS 包自己的文件,归 DS 包**,本包不收(归属判据见 §7.1 三条测试)。

```
① 用户:把 Figma 节点链接(含 node-id)发给 Chat
② Chat 直读:get_metadata(结构/节点ID)→ get_design_context(尺寸/布局/截图)→ get_variable_defs(颜色/语义 token 绑定)
③ Chat:裁决(**默认以 Figma 直读为准;skill 与直读不符即改 skill**——总则1)→ 赋予语义与规则 → 固化进 skill
④ Code:用固化值渲染校验图,与设计对照 → 改到像
```

**实测准入(铁律)**

1. **只有 Figma 直读值可入库**;读不到的(如封装在 SVG 内的圆角)标 ⚠ 未暴露,**不推导、不脑补**。
2. **变量绑定优先,但规范页压过变量**:`get_variable_defs` 的语义 token 绑定(如 轨道关=H3、滑块=CT6)直接采信,免去 hex 撞库;源稿**手写标注**与变量绑定矛盾时以**变量绑定**为准。
   > ⚠️ **变量与 Figma【规范页】矛盾时,以规范页为准**(用户 2026-10-26 裁定)。实证:CF6、CB12 / 22 / 25 / 38–40 黑版、H16 几处变量值与「色值规范」页对不上。两者**都在 Figma 内部**,总则1 只说「以 Figma 为准」、没说以 Figma 的哪一份为准——这条补的就是那个缺口。**规范页自身前后矛盾时报给用户,AI 不自行择一。**
3. **节点映射 Chat 自取**:源文件迁移后用 `get_metadata` 重新取节点 ID,不依赖历史 ID。
4. **完整性**:提取前先在 skill 找己方既有真值避免重复;多变体逐个读全,缺项显式标注。
5. **越界仍归 Chat**:直读只给「长什么样」;何时用、叫什么、什么语义 / 规则由 Chat 产出;skill 未覆盖的新信息列「待确认」,经用户确认才固化。
6. **🚧 字体替换硬规则**:直读 / 设计稿中出现 **DIN 系字体**(D-DIN / D-DIN-PRO / DIN Alternate 等)**一律改用 GJType**(国金自有数字字体)入库与同步——固化、校验图标注、回写 Figma 时都换;**仅换字族,字号 / 字重 / 行高不变**。(C 端数字字体统一 GJType。)
7. **🚧 图标优先用库(制作原型 / 预览硬规则)**:做原型 / 校验图 / 预览时图标**必须优先调 skill 图标库**(`assets/icons/`:通用→`common/`、场景→`{场景}/`)的真实图标。库里没有的:① 已有上传资产能补的先补入库再用;② 取不到 Figma 资产字节时需用户**导出 SVG 上传**补入库后用;③ 暂不可得则**显式标「⏳图标待补」征求用户**。库内确实没有的可手画占位(标「⏳占位,待替换」)。要点:**先查库、库里有就必须用库里的**,别在库已有时自创画法。

**校验图 =「按真值重建」+ 资产嵌入限制**:校验图按直读真值重建(尺寸 / 色值 / 布局 / 几何),**不是嵌入 Figma 原始资产**。本环境取不到 figma 资产字节(网络白名单不含 figma.com、沙箱不能加载 figma 外链),故**资产级矢量**(精确路径、内封圆角等)只能贴近重建并标 ⚠️;**需像素级 1:1 时走「用户导出 PNG/SVG 上传」**用真实资产再核(`get_screenshot` 的 base64 仅供 Chat 自检,不能直接嵌进交付物)。**重建 ≠ 原始像素须对用户讲明,不蒙。**

**不制造无谓询问**:Figma 已有明确样式的**先直读确认、以直读为准**。**仅两种情况才找用户:① 相比原方案 / 直读,确有更优替代;② 原方案 / 直读样式本身有问题。** 除此不发问;尤其**不拿自己都认为差的方案去问**(假选项凑数)。本该自己直读就能定的不变成提问。

**备用通道(trae)**:仅 Figma MCP 不可用时回退,按旧纪律(回传 md、A/B/C 格式、推导拒收、撞库比对);MCP 恢复后以直读复核为准。

### 4.2 源规范完善流程(触发:Figma/Design 源规范不完整)

源规范不一定完整(「????」占位、缺态、缺数值、不成体系)。此时不是"忠实搬运",而是 **Chat 主动完善**:

1. **取值优先级**:Figma MCP 直读优先(4.1)→ 不可用时截图 / 纯文字 → 仍不行回退 trae。
2. **不完整 = Chat 补全**:补缺态、系统化命名、定规则、补缺数值,而非纯搬运。
3. **忽略占位**:Figma 中「????」等占位文案一律忽略,不当内容。
4. **不确定就问**:拿不准的【规则】(用途、选用条件、命名、缺态)先问用户拍板;仅【像素级数值】可按既有规律给默认值,但须标「⚠️待确认 / 待提真值」。
5. **完善后仍走标准循环**:固化 → 校验图 → 用户确认 → 同步 Design;未确认不写完成、不升进度。

### 4.3 对账循环(触发:站点自行产出过内容、隔了几轮没同步、或视觉对不上)

> ⭐ **对账是双向的**:站点既可能**画错了**(→ 改站),也可能**检查出 skill 的问题**(→ 改 skill),**而且常常两者并存**。⛔ **不要套公式自动归位**——逐条判,判不了的交用户拍板;该看什么迹象见 `SKILL.md` §2 总则2 第二层。

> **A 之前先核版本戳**:对账第一步先看 Design 产物的版本号——**若 Design 版本 < 当前 skill 版本,即版本滞后、不是新 bug**;差异多半是"Design 还没拿到最新修复",应先让 Design 升到当前版再对,**别把滞后当问题重新诊断、重新出提示词**。版本一致后才进逐项 diff。

```
A 用户:Design 导出(html/zip)→ 拖进 Chat
B Code:解析并与当前 skill 逐项 diff → 输出【差异表】(项目 | skill值 | Design值 | 判定)
C 裁决:**逐条判它偏哪一种,不套公式;一条差异也可能两种都沾**——
   · 偏**情况1**(skill 对、站做错了)→ 改站,走 D / E。
   · 偏**情况2**(站检查出了 skill 的问题)→ 记成 skill 的待修项,走 D'。
   · **两种都沾** → **D / E 与 D' 都走**:站点先绕过去让页面能看,skill 侧那条照样记、照样修。
   · **判不了 / 两边都说得通** → 标 🚧 列出来交用户拍板(各给现象 + 实测数据 + 代价),**不自行择一**。
     判断迹象见 `SKILL.md` §2 总则2 第二层,此处不重抄。
D Chat:据差异生成同步提示词,每条注明「当前写错/缺失什么 → 应改成什么」,不只给目标值
D' 若 C 判出 skill 的洞:**逐条记进包外的验证反馈件**(现象 + 实测数据 + 建议),由 skill 签发方择时一批修;修完在该条后标 ✅ 与修订
E 用户:把 D 的提示词给做站那方 → 修正站点(同窗口做则直接改,不必转交)
```

> **对账须核到「资产级」**:B 的逐项 diff 不止比版式 / 数值,还要逐个核**用的是不是 skill 指定的确切资产**(图标文件名、token、参考实现)——版式像、但图标用了占位 / ≡、token 硬编码,都判**不通过**;资产不符**不得提前标「可验收 / 通过」**。
> 日常只走标准循环(先改 skill 再同步)就不漂移;对账是补救与校验手段。

**Design 回报形态规范**:Chat 发起进度对齐 / 盘点时,Design 回报须是**可直接复制的文案**(整段进复制框);**过长时整理成 `.md` 文档交回**,不以零散聊天长文本作对齐依据。盘点须:① 按批次标「本会话已做 / 既有未动 / 未做」;② 附偏差申报;③ 导出现状供 Chat 取证。

**多页站导出**:可视化站是多页结构,**不存在「全站单文件」**;按页 / 分册各自导出,Chat 按页取证;Code diff 以「本轮改动文件清单」为准。

> 站点版本戳的「应为哪版」不在本包裁——查包外**站点版本真值表**,并以其为差异表基准逐项核,**戳不符即判不通过**。

### 4.4 图标资产管理(触发:图标随组件出现)

> 🏷️ **本节属项目实例层**(见 `SKILL.md` §3.0「包分两层」):里面的具体值按本项目写,**换项目整节替换**;通用的是「要有这么一节」。

图标按"能否被字体承载"分两类(详见 skill 的 `assets/icons/ICONS.md`):

```
通用单色图标(返回/搜索/设置/分享…) → IconFont 字体(assets/icons/fonts/),<i class="iconfont icon-xxx">
渐变/特效图标(如底部导航选中态)   → SVG(assets/icons/bottom-nav/ 或 gradient/)
复杂动画图标(Lottie/逐帧)          → skill 只写引用说明,资源放外部
```

**判断**:纯单色无动效 → 字体;带渐变 / 特效 / 动画 → SVG/Lottie;**字体绝不能承载渐变与动画**。
**来源与传输**(Code 无外网):iconfont 字体由用户在 iconfont 平台生成后提供(或从 Design 产出 HTML 提取内嵌);渐变 / 动画 SVG 由用户从 Figma 导出提供。Chat 负责还原 + 生成 css + 登记 ICONS.md + 升版本。

**命名**:图标类名 / 文件名规则(`icf_*` / `slice_*`)的正文在 DS 包 `assets/icons/ICONS.md` §零,**本处不重抄**。本包只管两点:① 入库前按那份规则核名,**不按旧类名放行**;② **往 Figma 写图层时(§4.7),图标图层名同守这份规则**——两边不同名,下次就靠名字找不着了。

### 4.5 发布 / 部署上线(触发:可视化站取证通过、需要线上可访问)

```
① 取一份取证通过的自包含多页站(每页已内联,离线可开)
② 按【总则3.6】做文件名 ASCII 化与链接全量同步          ← 规范在总则3.6,本步不重述
③ grep 复核:旧中文文件名 + 旧 zip 名残留 = 0;站内 skill zip 是**当版**、PK 头有效、与权威包 md5 一致、**链接出现在 `index.html` 里**
④ 打部署包:最外层直接是 index.html + 英文页 + assets/(含站内 skill zip,Netlify 拖拽即用)
⑤ 上传上线;「下载 Skill 包」按钮点出去是 **GitHub 发布仓**,站内那份 zip 留作**自升级备用源**(§4.6)
⑥ 本地交付件归档                                        ← 规则见下方「本地文件归档」,本步不重述
```

**🚧 红线**:发布 / 部署**只动文件名与链接**;页面渲染 / 交互、token 数值、750 示例、壳层逻辑一律不变(总则3.6-5)。

**部署前固定核验项**:用户提出部署时,**必须先核**三件事——① 「下载 Skill 包」按钮是否指向发布仓;② **站内 skill zip 是不是当版、链接在不在 `index.html` 里**(自升级备用源靠它);③ 页面文案里有没有**写死的 skill 版本号**(写死就会跟着过期)。把差异摆给用户,由用户决定同批刷还是明知故留。位置与处数见包外**站点版本真值表**的「位置与处数」节,本处不重抄。
**部署时机由用户主动提出**,本窗口不主动提议、不催。

**维护方(Chat)亦可执行**:替换站内 skill zip、改部署结构、ASCII 改名、把下载按钮改指发布仓等机械操作 Chat 可直接代做(有源文件时),同守总则3.6 并做 ③ 取证。

**站内 skill zip 的更新时机**:它现在是**自升级的备用源**,不再是主下载点(主下载点是发布仓,§4.6)。**每次发版由用户本人同步到当版**(用户 2026-10-27 定)——**不出任务卡、不归 Design 窗口**;发布 / 部署阶段只负责**核**它是不是当版(见上「部署前固定核验项」),**不在组件级 Design 提示词里反复要求**(见 5.4-10)。

**本地文件归档**:发布 / 打包收尾时,各版本线只在原位保留最新交付件,旧版本移入 `历史文件/`。**够得到本机的窗口自己做**,够不到按 `SKILL.md` §3.3 分支③;判定与处置规则(规律明确才处理、拿不准标 ⚠️ 报回)见 `execution-standard.md` §八,本处不重抄。该规则只管维护工作区整洁,**不影响** skill 包内部版本、发布仓与站点下载区的版本、自升级机制或历史 CHANGELOG。

### 4.6 自升级机制维护(触发:改动可能影响 skill 自动更新)

**两个包都带自升级**:DS skill 自 v3.9.1 起,WF 工作流包自 **v6.10** 起。使用者启动时自动比对版本、落后则拉新版覆盖安装;**失败永不阻断**(任一异常都 `exit 0` 放行)。

**版本源两条,有优先级**(用户 2026-10-27 定):

| | 源 | 取版本的方式 |
|---|---|---|
| **① 首选** | GitHub 发布仓 `{发布仓}` 的 `{本包在仓里的子目录}/VERSION` | 直接读文件 |
| **② 备用** | `{站点}` 下载区的包文件名 `{前缀}-vX.Y.Z.zip` | 从 `index.html` 里解析文件名 |

> 🏷️ **这三个值属项目实例层**,真值在项目侧「协作参数」(`SKILL.md` §3.0)。**包内 `scripts/check-update.sh` 里的是某一个项目的默认值,不是规则的一部分。**

- **仓库读得到版本 → 以仓库为准**:不比本地新就静默结束,**不再看站点**;比本地新就从仓库取包,**取包失败才改从站点取**。
- **仓库读不到版本**(网络 / 仓库不可达 / 内容异常)→ 才改看站点。
- 两条路装包前都核对:包内有 `SKILL.md`,且**包内 `VERSION` = 该来源声称的版本**,不符就不装。

**耦合处**(改任一处都受下面的硬闸门约束):

- `scripts/check-update.sh`:**两个包各带一份,内容相同,只有 `SUBDIR` 默认值一行不同**(DS=`design-system`、WF=`workflow`)。站点备用源的包名前缀按 `SUBDIR` 在 `case` 里给默认值——**目前只给 DS 配了 `guojin-ds-skill`,WF 为空即「无站点备用、只查仓库」**;WF 日后要加,就在那个 `case` 补前缀或设 `GJDS_UPDATE_SITE_PKG`。
- `VERSION` 文件:本地版本号,**须与 `SKILL.md` 的 frontmatter `version` 和标题版本三处一致**(三处都写了版本,漏改任一处就对不上)。
  > ⛔ **只写这句没用,必须跑断言**——命令在 `SKILL.md` §2 总则3.3 条2,**打包前跑一次**。**实证**:本包 v7.0–v8.0 连续六版的 `metadata.version` 与标题都停在 `6.12`,而自升级**只核 `VERSION` 文件**,所以一路没报错。
- `SKILL.md` §0 开头的「升级自检」:有 bash 就跑,没有就跳过。
- **发布仓侧**:仓名 / 分支 / 子目录名固定,脚本据此取值。**发布仓自己怎么维护(推送时机、目录、包外资源、谁能做什么)见 §4.9**,本节只管它作为版本源的那一面。
- **站点侧**:`assets/{前缀}-vX.Y.Z.zip`,**包名前缀不可改、链接必须出现在 `index.html` 里、页面只留一个版本的链接**(脚本取第一个)。**每次发版由用户本人同步**,不出任务卡、不归 Design 窗口。

**为什么首选仓库**:旧机制只有站点一个源,而站点要靠人工同步才更新。**实测 2026-10-26**:站点停在 DS v3.29.4,当时实际已是 v4.1.1——**自升级跟着停摆了五个版本,没人发现**。
> **主版本源不能挂在一个需要人工同步的面上。** 发布仓既是下载点又是版本源,不存在「跟没跟上」;站点作备用,人工同步漏了也只是少一条退路,不再是单点。

**升版落地时同轮核对(治上面那个坑)**:任一包升版后,**当轮**核一次——发布仓推了没、站内那份 zip 是不是当版、页面文案有没有写死 skill 版本号。**不等下次有人顺手勘察才发现**。核验口径见 §4.5「部署前固定核验项」。

> **⛔ 覆盖安装只用 `rsync -a --delete`;本机没有 rsync 就不装、明着报一行。** 不回退 `cp -rf`——它**不删文件**(新版删掉的留在本地,装完目录指纹**悄悄偏离签发件**),而且**原地截断重写正在运行的脚本自己**(bash 按偏移续读,执行会错乱)。**实证**:这两个缺陷在 DS 包里从 v3.x 一路带到 v4.1.1 没被发现,因为当时没有任何闸门要求跑一遍包内脚本,而**有 rsync 的机器上它们根本不出现**。闸门已补在总则3.3-细则。

**🚧 硬性要求(不可降级,见 `SKILL.md` §1 总则0①):任何可能影响自升级功能的改动,必须事先「重点 · 显式」向用户说明影响面、取得确认后才动,不得静默改。** 涵盖:`check-update.sh` 逻辑(两条版本源的取法与优先级 / 比较方式 / 下载与安装分支 / 代理 / 超时 / 子目录定位)、`VERSION` 文件存废与语义、`SKILL.md`「升级自检」存废或行为、**发布仓的仓名 / 分支 / 子目录名**、**站点下载区 zip 的命名 / 路径 / 链接是否在 `index.html` 里**。
常规组件 / token 改动不受本条约束(但其版本号变化仍照总则3)。

#### ⛔ 把包分发给别人时 —— 换掉**交出去那一份**的自升级默认值

`scripts/check-update.sh` 里 `REPO` / `SITE_BASE` / `SUBDIR` **带的是分发方自己项目的默认值**。不换就分发,会这样:

| 现象 | 后果 |
|---|---|
| 接手方每次开窗跑自检 | 从**分发方的仓**读版本 |
| 分发方的仓里版本更高 | **整包覆盖接手方手上那份**(`rsync -a --delete`) |
| 接手方自己改过包 | **改动被静默盖掉**——脚本设计上「失败永不阻断」,成功时也不问 |

**所以分发前必须做一件事,三种做法任选**:

1. **把那三行默认值改成接手方的**(他自己的仓 / 站 / 子目录);接手方没有发布面 → 设成读不到的值。
   > ⛔ **改的是「交出去那一份副本」,不是你自己留着的那一份。** 你那份指向你自己的仓**是对的**——那就是你的发布面;动了它,**你的自升级当场断掉**。打包给别人时改副本,本地那份原样不动。
   > ⚠️ **实证(本条就是这么被读错的)**:v9.2 写下这条的**当天**,本包签发方自己把它读成「改包里的默认值」,还向用户提议「要不要把那三行也改掉」——**规则落地一天就被它自己的作者读错一次**。根因是这一条**只说了改什么、没说改哪一份**。v9.3 补。
2. **或**让接手方 `export GJDS_UPDATE_REPO=…` 覆盖(他每个会话都要 export,**容易漏**,只适合临时);
3. **或**接手方不要发布面 → `export GJDS_UPDATE_REPO=none`,并在他的参数件里把「对外发布面」记成**无**。

> ⛔ **别以为改错了会退回站点。** 站点备用源**只对配了包名前缀的子目录有效**(脚本 `case` 里按 `SUBDIR` 给默认值,**没配的一律为空 = 无站点备用、只查仓库**)。所以对没配前缀的包,`REPO` 一改错 / 一清空,**两条源全断**。
> **实测(2026-11-09,本包)**:`GJDS_UPDATE_REPO=none/none` → 输出「仓库读不到版本,改查站点…」→「**本包无站点备用源,用本地 X.Y 继续**」→ **退出码 0**。
> ⚠️ **这个故障完全无声**:自升级的设计是「失败永不阻断」,所以它既不报错、也不非零退出,**只是从此再也不升级了,没人会发现**。改完务必跑一次看输出,别只看退出码。

> 🚧 **改那三行落在本节的硬闸门里**(上一条明列「发布仓的仓名 / 分支 / 子目录名」)——**要先把影响面摆给用户、取得确认**,不得静默改。**但「不换」也是一个决定,而且后果更重**:所以分发这件事本身就要向用户摆明这两条路,让他选。
> ⚠️ **自升级自检:必跑一次**(口径在 `SKILL.md` §0;「跑不了不阻断」说的是**失败**,不是「可以不跑」)。**只有一种情况要先断开再跑**:**分发方的仓里那一版可能比你手上这份新**(刚从别人那儿拿到包、对方的仓还在维护)——那时先定 `{发布仓}`,或 `export GJDS_UPDATE_REPO=none`。**仓里不比你新 → 脚本 `is_newer || exit 0` 静默退出,照常跑就行。**
> ⛔ **本条与 `SKILL.md` §0 必须同口径。** v10.0 只改了 §0、**漏了本处**,于是本处留着一条反口径的「第一轮不要跑自检」,还声称「操作卡已写」——**指向了一个已经不存在的说法**。实测(2026-11-09 冷启动):窗口两边一对照判不了,**结果干脆没跑**。改一处必回扫另一处,通则见 `multi-window.md` §8;**凡句子里带「(X 已写)」这种交叉声明,改 X 时一并回扫**。

### 4.7 Figma 写操作(触发:**凡对 Figma 做写操作**——把已固化真值反向建 / 改组件、新建组件或组件集、从设计稿复制再改成组件、整理稿件、改绑变量)

**本节管的是「往 Figma 里写」这件事本身,不限于「把 skill 真值写回库」。** 从设计稿复制出来再改成组件、在 Figma 里新建组件集、只改一个变量绑定——**一样适用本节的全部条款,不是只适用前置纪律**。(`use_figma` 经 Plugin API。)**写操作有成本、不可逆,前置纪律从严:**

> ⛔ **实测(2026-11-09 冷启动)**:v10.0 本节触发条件只写了「把已固化真值**反向建 / 改**」,窗口做的是「从设计稿复制再改成组件」,**判定触发条件不匹配**,于是——用它自己的话——「**下意识只把前置纪律当成适用,具体操作那几条没往自己身上套**」,变量绑定整块没做。
> **这是「章节的触发条件写窄,把同类活动排除在外」**,与 v9.3(作用对象没写)、v10.0(触发条件没写)**同族**;通则已收进 `multi-window.md` §8 第四问。

**前置(每次必做)**
- **成本意识**:`use_figma` 写操作消耗较多点数。能用 skill 真值 + 校验图表达的优先用;**Figma 绘制按需、且必经用户显式"可以"才动手**(写操作属两次确认外的额外闸门)。
- **加载技能**:动手前必加载 `figma-use`(API 规则)+ `figma-generate-library`(建组件流程);调 `use_figma` 时 `skillNames` 传 `"figma-use,figma-generate-library"`。
- **保留原内容**:同步默认**新建组件、不原地改原件**。

**字体配方(本环境关键坑 —— 只管「在 Figma 里怎么把字体加载上」)**

> 🔴 **「必须用哪个字体」不在本节**:那是**渲染比对图**的硬规则,在 **§5.2**(连「装不上要怎么显形」一起)。本节只管 Figma 环境内的加载手法。

> 🏷️ **实例层 + 有保质期**:下面的可加载字体清单是**某个环境在某一天的实测值**,换环境 / 过一段时间都要重测一次,**别当长期事实引用**(`SKILL.md` §3.0)。
- 本环境 **PingFang SC / GJType 等不能直接 `loadFontAsync`**;可加载实测:Inter / Roboto / Noto Sans SC / Noto Sans ✓,Arial ✗。
- **配方**:① 用 **Noto Sans SC** 打底 `createText` → ② **先把 `fontSize`/`lineHeight` 定到目标值** → ③ 再 `await t.setTextStyleIdAsync(样式ID)` 套库内文本样式换字族(中文 `S8-CN-R`=PingFang 20/30、数字 `S7-NUM-M`=GJType Medium 24/36)。
- **反例**:不预定字号直接 `createText`(默认 12px)→ 套样式 → 重排需加载 PingFang 而加载不了 → **静默失败**,字形停在 ~12px,样式面板仍显 20/30(标签对、字形小)。
- 承 4.1#6:见 DIN 一律改 GJType;涨跌幅符号统一 GJType。

**布局 / 高度**
- missing-font 会让 auto-layout 文本盒按字形收缩 → **组件高度显式锁**:`counterAxisSizingMode='FIXED'` + `resize(w, 目标高)`。
- **不能原地改 unloaded-font 文本**:改字号 / 字族会 throw `unloaded font` → **要改就删了重建**。

**变量绑定**:`getVariableByIdAsync(id)` → `figma.variables.setBoundVariableForPaint(paint,'color',v)`(返回新 paint,回写 `node.fills`/`strokes`)。按变量**叶名**匹配定位 ID(如 `CP0`/`CL3`/`CB13`)。底 / 字 / 描边都绑;无对应变量的才用 raw + opacity。

**建组件流程(小步 + 校验 + 确认)**
1. 只读探查:页面 ID、放置空位、所需颜色变量 ID、字体可加载性、文本样式 ID。
2. **先小范围试做一个** → `get_design_context` 截图核实 → 用户确认"第一次效果"。
3. 确认后再建其余;每建一个截图核一次。
4. `combineAsVariants` 后变体堆叠在 (0,0),需手动栅格 / 换行(`layoutWrap='WRAP'` + 固定宽);二维属性用变体名 `属性A=值, 属性B=值`。
5. 组件 `description` 填一句使用说明。

**API 纪律(figma-use 铁律)**:颜色 0–1 区间;`fills`/`strokes` 只读数组,克隆改回写;**每个 Promise 必 `await`**;**page context 每次重置**(脚本开头 `await figma.setCurrentPageAsync(page)`,一脚本至多切一次页);**绝不并行 `use_figma`**(状态变更须串行);脚本出错是原子的——读错误、改对再重试,不盲目重试;**返回所有 created/mutated node ID**,不臆造。

### 4.8 生成页面的可靠性三层(触发:用 skill 出任何页面 / 原型)

把"使用者能生成符合规范的页面"从「靠模型自觉」改为「靠机制」。规则写进文档 ≠ 模型执行时会查库,故三层缺一不可:

1. **降摩擦(第一层)**:一切可复用资产登记在 `assets/library-index.json`(图标 / 组件 / token → 库内确切引用),配 `icon-palette.html`;资产变动后重跑 `scripts/build-index.py`。让"照抄库内引用"比"手画 / 重写"省事。
2. **强制产出 BOM(第二层·闸门 A)**:动手前先出《用料清单》表——每个图标 / 组件 / token 写明库内引用,查不到才标 ⏳。**BOM 填不出 = 没查库。** 反复嵌套复用的组件一律指参考实现、不就地重写。
3. **确定性校验(第三层·闸门 B)**:交付前必跑 `scripts/check-page.py 页面.html`,**P0=0 才准交付**,P1 逐条复核。模型会忘,脚本不会。

**铁律**:闸门 A、B **不可跳过**;影响三层的改动(索引结构 / 生成器 / 校验规则 / 闸门文案)按 4.6 同级,经用户重点确认。

### 4.9 发布仓维护(触发:要推新版、要放包外资源、要打 tag)

> 🏷️ **本节属项目实例层**(见 `SKILL.md` §3.0「包分两层」):里面的具体值按本项目写,**换项目整节替换**;通用的是「要有这么一节」。

> 本节管**发布仓本身**;它作为自升级版本源的那一面在 §4.6,两节不重叠。

发布仓 `{发布仓}` 现在**同时是两种面**,节奏不同,别混着管:

- **两个 skill 目录**(`design-system/` · `workflow/`)= 阶段性对外发布面——**有阶段性成果才推,日常迭代不走这里**。
- **`site/`** = 可视化站的部署源(2026-11-04 起 Netlify 从本仓自动发布)——**站点改一次就要推一次,它是日常面**。

**目录与 tag**

| 顶层 | 装什么 | 跟 tag 吗 | 谁维护 |
|---|---|---|---|
| `design-system/` | DS 包解压后的内容 | ✅ 跟 | 该包签发方 |
| `workflow/` | WF 包解压后的内容 | ✅ 跟 | 该包签发方 |
| `resources/` | **不进 skill 包的外部资源**(动图、视频、大体积素材) | ⛔ **不跟** | 引用它的那条线 |
| `site/` + `netlify.toml` | **可视化站部署源**(`publish = "site"`) | ⛔ **不跟** | **站点线**,别的窗口不要动 |

> tag 是「**这一刻两个包各是哪一版**」的快照,**不是第三条版本线**;`resources/` 不属于任何一条版本线,所以不跟 tag。

**⛔ 往仓里放「有既有线上版本」的东西之前,先做一次逐文件防回退比对**

判据:**这个东西在仓外已经有一份正在用的版本吗?**(线上站点、已发布的包、别人正在引用的资源)——有 → 先比对再推。

- 比的是**你手上这份 vs 当前正在用的那份**,**逐文件**,不是打开首页看一眼。
- 站点类的判据沿用**站点版本真值表**的「防回退比对」判据,此处不重抄。
- 比不出来就别推,先问持有方(站点归站点线,包归各自签发方)。

> **为什么要单写一条**:§6 自检7 的回归检查与总则4 的出包前核范围**只管 skill 包打包**,管不到「往发布仓提交别的东西」。闸门缺在这儿,而这儿恰好是**唯一能无声覆盖线上成果**的地方。
> **实证(2026-11-04)**:改 Netlify Git 自动发布时提交进仓的那份 `site/` 是**九月之前的旧导出**——全局版本戳 26 处停在 `v3.11.0 · 20260615`(当版应是 `v3.20.1 · 20260915`,新值零处)、v3.20.1 已整体删掉的 12 处文件头注释又回来了、v3.21.0 落地的模块戳只剩 9 个。**一旦部署,线上站点退回两代、三天的工作无声作废,而页面照常打开、不报任何错。** 靠别的窗口顺手核了一遍才发现。

**包外资源(`resources/`)**

- **什么该放这儿**:体积大、或与规范正文无关、进了包会拖慢每次分发的资源。**判据:它变了要不要升 skill 版?不要 → 放 `resources/`。**

### 4.10 从成品页拆组件(触发:拿到一张已做好的页面 / 整份设计稿,要判「哪些引用通用组件、哪些要新做」)

**本节是 §3「一个组件一轮」之外的另一个入口。** 主流程假设你**已经知道**要做哪个组件;本节解决的是**还不知道要做哪些**。

**步骤**

1. **取证**:整页截图 + `get_metadata`,拿到图层树。
2. **列实例**:把页面里**所有外层实例**的主组件 key 列出来——**只列最外层,不下钻**(嵌在组件内部的原子归它的主组件管)。
3. **比编码表**:逐个比被维护 skill 的组件编码表(本项目是 `figma-codes.json`)。**命中 → 通用组件,直接引用,不做**;**未命中 → 候选业务组件**。
4. **归类未命中的**:按截图 + 图层名 + 关键数值对照速查卡归类。⚠️ **「编码表里没有」≠「它就是业务组件」**——归属照 `SKILL.md` **总则7** 判(≥2 个场景用到 → 通用;只有单一场景 → 业务);**拿不准的标 🚧,不猜**。
5. **出拆分图 + 清单**给用户拍板:哪些引用通用、哪些新做、哪些拿不准。**这是说明图,必配**(`SKILL.md` §2 总则4)。⚠️ **这一次拍板属「确认前置」,不替代后面每个组件各自的两次确认**(同上)。
6. 拍板之后,每个要新做的组件**各自回到 §3 主流程走一轮**。

⛔ **判「这个是不是和通用组件重复」只有一个合格做法:读组件库现行组件的原件,数值逐项比。**

- **不凭图层名判** —— 图层名是上一个作者起的,和库里叫什么、是不是同一个东西没有必然关系。
- **不只看文字规格判** —— 规格描述得再像,数值可能完全不同;反过来也一样。
- **只是外壳不同(容器、留白、背景)的** → 写成**通用组件的场景覆盖**,**不单独建组件**。
> **实测(2026-11-09 冷启动)**:同一个标题栏被判了三次、用了三种方法——① 读文字规格比 → ② **只看图层名就判成「引用 C04」(错)** → ③ 去库里读现行组件原件比,才发现只是外壳不同。**白走两轮。**

⚠️ **设计稿整份连的是旧组件库时,第 3 步会整片落空。** 出现「数值对不上库、但页面看着没错」时,**先核主组件是不是旧版**,别急着归罪于被维护 skill——同一实测里,图标小 2px 一度被误判成 DS 图标字体的问题。**具体怎么判归被维护 skill 管,去它那儿查。**

## §5 产出标准(各类交付物"做成什么样"才合格)

### 5.1 组件抽象与复用

- **通用 vs 专属分清**:通用组件规格写成"可配置"(如底部导航 tab 数与图标可替换、建议 ≤5),示意图标标"仅示意"且用专用图标集 active+inactive 配对;专属变体单独成组件,不混入通用;拿不准问用户。
- **复用优先,旧组件必须嵌套**:新组件若含已有组件的样式 / 结构(按钮、图标、tab、标签、分割线、胶囊等),**必须以「实例嵌套」复用**,不重画 / 复制样式另起一份;固化时写明"由 XX、YY 既有组件嵌套组成",不把子组件尺寸色值再抄一遍。是否等同已有组件、该不该复用,**先与用户确认**。好处:改底层,上层自动跟随。
- **交互以文字规范沉淀**:交互行为(点击切换、滚动响应)写进 skill 作文字规则;是否做可点击 demo **按用户要求**,不擅自加用户没要的交互演示。

### 5.1b 参考实现:组件本体 vs 演示外壳,以及「这份文件服务谁」

**参考实现 HTML 里有两种东西,先分清再动手**:

| | **组件本体** | **演示外壳** |
|---|---|---|
| 指什么 | 被固化的那个组件自身 | 标题、说明、规格卡、排版网格、主题切换、交互控件、来源说明 |
| 真值来源 | **Figma 直读**(总则1);无设计图时按规范近似值 | **一律用规范值**(token),不另立数值 |
| 改动要求 | 任何改动都要做回归比对(§6 自检5) | 同样要 token 化 / 规范化 |
| 尺寸变化 | 算回归,要解释 | **不算问题** |
| 上不上站 | **上**(Design 同步的就是它) | **不上站** |

**⛔ 生成前先定「这份 HTML 主要服务谁」,默认只选一个主用途**:**参考实现**(默认,一个主预览 + 必要变体,**不自动展开成完整测试矩阵**)/ **效果确认页**(给用户拍板,看完即弃)/ **测试页**(覆盖边界异常,内部用)。

- **每个可视模块要回答一个独立问题**;主预览已能表达的,不再复制一组状态卡片(§7.1 载体对照表)。
- **变体与边界优先写进实现规则与自检,不默认做成展示模块**;要留的信息放进 DOM / CSS / BOM 与简短说明。
- **借别的组件只借组织结构,不继承它的视觉布局**——视觉真值只认 Figma 与该组件自己的规格(总则1)。
- **实证**:C09 进度条第一版把参考实现、人工效果确认、内部测试矩阵三种用途做进同一份 HTML,组件本身没有交互却出现了「交互试验台」标题,页面更像测试报告。

### 5.2 校验图(1:1 还原方法论)

> 🔴 **字体硬规则(与环境、与渲染方式无关,不可降级)**:**凡渲染要拿去和设计稿比对的图,文字必须用被维护 skill 规定的字体。**
> 装不上 / 加载不了时:① 先试**内嵌**(base64 / `@font-face`);② 实在不行,**必须在交付里明写一行**——「本图用 {替代字体} 渲染,字形与设计稿不同,**不可据此比对字形**」。
> ⛔ **不许静默降级。** 自己知道、用户不知道,等于把一张不可比的图当可比的图交出去。
> **规定用哪个字体是被维护 skill 的真值**(去它那儿查);**本节只管两件事:必须按它、降级要显形**。通则见 §6。
> **实测(2026-11-09 冷启动)**:窗口的对照图用 Noto Sans CJK 渲染(本机没有 PingFang),**它自己知道,但 17 轮里一次都没说**。用户裁决:「应该用 DS 规定的字体的。」
> ⚠️ **本条放在这里、不放 §4.7**:§4.7 的触发条件是「对 Figma 做写操作」,而**渲染比对图根本不走 Figma**——写在那儿等于再犯一次「章节触发条件写窄」(`multi-window.md` §8 第四问)。§4.7 只留 Figma 环境内的**字体加载配方**。

1. **真实 iconfont 字体**:通用图标用还原的 woff2 + `<i class="iconfont icon-xxx">`,不用 emoji / 手画凑;**渲染截图前等字体加载完**。
2. **Figma 绝对值布局**:尺寸 / 间距 / 字号直接用提取的 750 实测值,不靠"大概比例"。
3. **真实状态栏组件**:复用 `assets/components/status-bar.html`;wifi 扇形画不准就用 "5G" 文字替代。
4. **自适应 flex,不写死宽度**:容器 `width:100%`、操作栏 `flex space-between`、左右组 hug——对应 Figma 的 fill/hug。
5. **渐变 / 特效图标用内联 SVG / img**:从 skill 资源读 SVG;示意图标用专用图标集 active+inactive 配对,不用无关字体图标顶替。
6. **可交互组件一份 HTML 两用**:可交互组件的效果确认**以 HTML 做一份**,过确认后直接沉淀为该组件参考实现(`assets/components/xxx.html`),不另造静态校验图;简单 / 非交互组件用 inline 可视化快速确认。

> 复杂图标(如微信 capsule 内靶心、关闭 ⊗)手画易错,精度不够时走 4.1 要精确参数,**不硬猜**。

### 5.3 固化文本(校验图文案 ≠ skill 文案)

校验图标注是**校对速记**(允许混排、缩写、口语),不是规范文本。固化进 skill 时:

1. **必须按标准结构重写**:组件定位(是什么 / 用在哪)→ 构成与嵌套 → 变体与参数表(档位 / 字号 / 颜色,引用 token)→ 行为规则(交互 / 滚动 / 选中态,与静态样式分开)→ 备注(源稿差异与裁决)。**不照搬校验图文案。**
2. **规则归属分明**:不同组件规则分开写、不混述;一条规则只写在它所属组件下。
3. **用户只确认两次**:校验图一次(数值与效果)、skill 文本一次(表述与归属,可抽查)。

### 5.4 Design 提示词

> ⛔ **先判要不要跨窗口。** **同一个窗口里做完 skill 顺手做站,本节整节不适用——不需要给自己写提示词。**本节只管**分窗口做**时那份转接件。是一个窗口做还是分窗口做,**由用户定**(`SKILL.md` §3.1)。

> 复制框骨架 → `assets/templates/design-prompt.md`,**照抄,不自创**。

1. **主交付物 = 参考实现文件本身,不是 prose 重述**:固化组件 / 场景给 Design 时,**首选直接交付该组件的参考实现文件(HTML/CSS/SVG)+「1:1 照此渲染:图标 / 资产一律用文件内的、禁自画 / 内联近似 / 自行简化」**;prose 复制框退为"差异说明 + 归属 + 版本",不充当 Design 重新理解重画的唯一依据。原因:参考实现是像素级正确的唯一真源,Design 吃 prose 重画 = 每个表述缝放大成一整轮。**能给文件就别让它重画。**
2. **从 skill 生成**:对外同步表述一律以 skill 固化后文本为源,不从校验图复制。
3. **只含定稿表述**:全部是已确认的最终规范,用规范口吻陈述;不出现「决议 / 待确认 / 源稿已废 / 讨论过程」等过程性表述(纠错指向除外,且只说"应为什么"不说"为什么改")。未决项先问用户拍板,拍板前不进提示词。
4. **写差异 + 纠错指向**:只写差异、不让整页重做;每条注明「当前写错 / 缺了什么 → 应改成什么」,给规则与意图,措辞清晰简洁。
5. **定位用站点实际页面名**:每条提示词显式注明更新位置(哪个页面 / 哪个章节区块);Design 不得新开页面,除非明确写「新开页面」。**新固化的业务组件 / 场景须用 Design 站【实际页面名】指明归属业务页**(对账时已知站点结构,如行情→`scene-quote.html`),并写明"作为该页新增区块加入(非新开页面)";**不用逻辑名(如「自选页」)虚指。**
6. **全站可稳定预览 + 导出件自包含**:所有页面在制作全程任何时候打开都不报「未发现文件」/ 空白。**根治机制**:交付 / 导出的每个 HTML 页面必须**自包含、零外部依赖**——把共享 shell 的 CSS/JS、nav-data 在导出时**内联进每页**,不残留指向未随包文件的 link/script。Design 内部作者态可保留单点真源,但**导出动作必须内联**。此为常驻要求,不必每轮在提示词重复。
7. **明暗双版组件的展示方式**:带白 / 黑版(浅 / 深双版)的组件,在站里**展示须跟随网页明暗主题切换**(白肤显白版、黑肤同处切黑版),**不在同一主题下并列静态铺两版**。组件底色真值不变,这里约束的是"展示哪一版"。
8. **开头注明版本号**;按 `SKILL.md` §2 总则6 以复制框交付。
9. **复制框执行回执**:每发出一份 Design 复制框后,发下一份前**必须先问用户上一份的执行 / 落地情况**(是否做完、是否需先对账),确认后再发新的。
10. **不夹带下载入口与版本文案**:组件级提示词只描述"该组件 / 页面在站点的还原",**不夹带下载按钮改动、站内 skill zip 的替换、也不要求页面写上 skill 版本号**(那些归发布 / 部署阶段统一核,站内 zip 更是由用户本人同步,见 4.5 / 4.6)。
11. **不默认要求 Design 导出**:组件级 / 区块级提示词**不附「做完请导出」**——整站导出耗用户点数,改完让 Design 回一句确认即可。**仅两种情况明确索取一次导出**:① 需对账取证(4.3);② 打包 / 部署前(4.5)。同一份导出可兼作两用,**不重复索取**。
12. **不写未确认的他方执行状态**:正文只列本份**已确认定稿的当版差异**;不夹带"若上一批某项未完成则继续 / 补做"之类未确认 carry-over(靠第 9 条口头跟踪)。

## §6 输出前自检(Chat 每次给用户内容前必做,不可跳过)

**任何交付物(预览 / 规格 / 提示词 / 文件)发给用户前,先过这份自检,确认无误才发。**

0. **源数据全量比对(最高优先,先于一切)**:交付物中每一处数值 / 属性 / 状态,逐项对照已提取真值与用户决议核一遍;**凡某轮出现修改,即说明存在偏差,必须触发整体重新匹配**(不是只改被指出那处);真值未覆盖或含义不明处列清单问用户。
1. **精确读取**:数据逐处读准(必要时放大、用 Code 提取),不靠记忆;读不准标 ⚠️,不蒙混。
2. **常识校验**:对照参考或自行推理,矛盾或不确定先问用户,不擅自定。
3. **一致性校验**:token 是否存在、白黑版是否成对、字号↔S编号↔token 对应、与已固化内容是否冲突。
4. **自我覆盖检查**:多处编辑同一文件后,确认没把已有内容意外删除 / 覆盖。
5. **渲染确认(视觉比对,不只看一眼)**:渲染校验图后自己 view 并**逐项比对**——背景 / 白底、边框、圆角、元素齐全、颜色、无透底 / 错位 / 缺失。**自适应宽组件必须放在"宽于内容"的容器里渲染**,否则"等分填充 vs 写死宽 / 左对齐留白"看不出。走 inline 可视化拿不回渲染像素时,自检5 以"代码级逐项核对数值 / 色值 / 状态"为准;需像素级时产出 HTML 由 Chat view 后逐项比对。
   > **⛔ 批量替换类改动(改 token 名、换写法、引用 token 化)光看图不够**,必须做**改前 / 改后计算样式的逐元素比对**(颜色、圆角、间距、位置;浅色暗色各跑一遍),**0 差异、或差异逐条能解释**,才算通过。
   > **为什么**:这类错肉眼看不出、脚本也不报。**实证**:DS v4.0.0 把 SP/RD 定义写进了 `bottom-nav.html` 的**文件头注释**里,页面引用的 `--SP*` 全部没有定义、按 0 计算,高度从 1153 缩到 951;此后 v4.0.1–v4.1.0 跑 `validate.py` 都是 0 P0,**连四版没被发现**,直到 v4.1.1 做比对才查出。`sandbox-header.html` 少 5 个 token 副本、`var(--RD8)` 算成 0px,同样是比对才发现的。
   > 反过来,v4.0.2 / v4.1.1 两版正是用这个方法当轮抓出了 `clamp(0,…)` 失效这种看不出来的错。
6. **反推自检(语义自足)**:写完 skill,**只读刚写的规则文字、不看参考实现**,自问"能否唯一重画出合规效果?"——画不出或会发散(资产没钉到该层精度、自适应 / 状态没说清),即规则有洞,补到自足再收口。**组件 / 场景首次固化前,反推审走【整条规则、不只改动处】**——一次把潜在缝挖干净,别哪痛医哪、分多轮挤。并同时做**内部自洽核**:参考实现 ↔ prose ↔ token/资产 三方逐项对一遍,防自埋矛盾。
7. **回归检查**:在已有版本上改动后,对照上一版确认**只改了该改的、没弄丢已确认的**;改 A 不悄悄破坏 B。
8. **版本标注**:**已签发**的交付物带当前版本号;**预览 / 草稿带轮次号 `r{n}`、不带资产版本号**(总则3.2);预览标清「已读到 / ⚠️待确认」。
   > ⛔ **出包时另加一项:跑版本号三处一致断言**(命令在 `SKILL.md` §2 总则3.3 条2)。**眼看过不算**——六版都是眼看过的。
9. **交付节制——双向:该发的要发,不该发的不发**(治过度交付 / 浪费用户点数)。present 前**逐个过每个文件,只发用户此刻真正需要的**(决策项 / 效果确认图〔若需〕/ 最终交付物)。
     不能就补(截图 / 标注 / 对比表)。**说「本窗口出不了图」之前先试一次**——试过确实不行才给「原文摘录 + 精确位置 + 表格对照」,并注明是哪个窗口、试了什么(`SKILL.md` §2 总则4)。
     > 这条管**说明图**,下面三条管**渲染图**,**两者不是一回事**——对照表在 `SKILL.md` §2 总则4。把它们混成一条,要么回到乱发图,要么回到纯文字没人看懂。
   - **内部自检产物不发**:核对齐 / 色值 / 数值用的渲染图、量算、中间件是验证手段,**默认不 present**。
   - **渲染图只在「用户须看效果拍板」时才发**,且**数据要真实有代表性、能据以判断**;劣质 / 重复假数据的图不发。
   - **发了不许自我否定**:不得 present 一张图又说"这图不重要 / 看文件吧"。要么给能确认的,要么不发。
   - **每个交付件标明用途**(给用户确认 / 给 Design 用 / 留档)。

> 🔴 **通则 · 任何自动降级都必须在交付里显形。** 字体装不上落到替代字体、渲染拿不回像素改走代码核对、工具不可用改走手算——**只要实际做的和规则说的不一样,交付里必须有一行写明「降级成了什么、因此哪一项不能据此判断」**。
> **为什么收成通则**:自升级「失败永不阻断」让故障无声(§4.6)、渲染字体静默落到替代字体让对照图失真(§5.2)——**同一个毛病:降级了,但只有执行者知道**。

**强制执行**:每条在每次 present 前实际走一遍,尤其第 5、6、7、9 条针对视觉 / 语义 / 交付。**跳过自检直接让用户确认 = 流程违规。**

## §7 不重复原则与活动件维护

### 7.0 载体按「频率 · 写入方 · 读取时机」三轴分,不按「主题」分

**同一个载体里,变更最快的那部分决定整体节奏。** 把月级的背景和轮级的工单放一个文件,结果就是这个文件每轮都动。
**同理:把只有一方能写的东西和多方要写的东西放一起,就得多方都去动那一份;把「触发才读」的东西塞进必读件,必读件就没人读完。**

⛔ **这三件不是三条独立建议,是同一个判据的三根轴**(v9.1 合到一处;v9.0 之前频率在本节、写入方在下一节、读取时机根本没写):

> ⛔ **「触发才读」= 触发的那一刻读,不是开工时预读一遍就算。** **预读过的,动手前照样要重读那一节。**
> **为什么必须写明**:**预读比不读更危险**——没读的人知道自己没读、会回去查;**预读过的人以为自己读过了,凭模糊印象就动手**。
> **实测(2026-11-09 冷启动)**:窗口第 1 轮整份读了本文件,**动手做 Figma 组件集却是第 13 轮**,中间隔十几轮「只剩模糊印象,又没回去重读」,于是 §4.7 的**变量绑定整条被漏掉**,到第 16 轮用户点出来才补绑 71 处。

| 轴 | 问什么 | 分错了会怎样 | 实证 |
|---|---|---|---|
| **变更频率** | 这条内容多久变一次? | 慢的那份被快的拖着**整篇重写** | 校验台账涨到约 40KB、一天被整篇重写五次(§7.4) |
| **写入方** | 谁能写它? | 多方**互相挤掉对方的段** | 两次整篇覆盖事故(`multi-window.md` §8) |
| **读取时机** | 开窗必读 / 开工前 / **触发才读**? | 必读件塞满只在特定动作时才用的东西,**于是没人读完** | 入口 `SKILL.md` 一度 441 行、仍被要求全文必读(§7.1) |

| 频率 | 载体 | 装什么 | 谁写 | 何时读 |
|---|---|---|---|---|
| **阶段 / 月** | **档案件** | 背景 · 目标 · **阶段与里程碑** · 当前基线(**只版本号**)· 协作指引 · 踩坑 · 已否决 | 各线 | **开窗必读** |
| **换人 / 换机器 / 换载体才变** | **参数件**(§3.0 问来的那组值) | 设计真值来源 · 权威副本位置 · 路径 · 版本线与签发方 · 发布面有无 · 协作形态 · 活动件实际书名 | 任何窗口(每行写「定于」) | **开窗必读** |
| **轮 / 天** | **一份专门的在途件,按线分段** | **还没完的事**:逐项待办、卡在哪、逐格进度、发布面现状与口径 | 多方,**按线分段** | **开工前** |
| **随升版** | 各资产自己的 `CHANGELOG.md` / 待补段 | 每版改了什么、为什么改、内容勘误 | 该资产签发方 | 触发才读 |
| **出包当轮** | **校验台账** | 每个已签发包的校验值与核验状态(见 7.4) | 该版签发方 | 触发才读 |
| **一次性** | 任务卡与反馈 md | 某轮做了什么(过程件) | 出卡方 / 执行方 | **用完即弃** |

> ⛔ **「轮 / 天」那行原先写的是「各线自己持有」,那是个洞(v7.3 修)。** 「各线自己持有」在实践里等于**活在那个窗口的对话里**——**窗口一关就没,而且别的窗口看不见**。轮 / 天 的东西变得快,但**不等于可以不落盘**:它同样要有持久载体,只是**不能跟月级的东西混在一个文件里**。
> **怎么既分频率又不互相覆盖**:**一份在途件、按线分段、各线只动自己那段**(见下「每份活动件必须声明写入方」)。

#### 要不要再开一份? —— 拿三轴去量,别凭感觉

⛔ **角色不等于文件。** §3.0 列的是**角色(落点)**,不是**文件数**。一个角色完全可以和另一个合在同一份里——**条件是三轴都相同**。

| 量出来的结果 | 怎么办 |
|---|---|
| **三轴全同** | **必须合并。** 分成两份就是同一批信息的两处,必反向漂移(§7.1) |
| **任一轴不同** | **必须分开。** 合着就会犯那根轴对应的那个毛病(见上表「分错了会怎样」) |

- **先合并,再开新的**:想新开一份时,**先对着三轴找现有的哪一份轴全同**——有就写进去,别另起文件。`multi-window.md` §8「别再派生新文件装规则」是同一条纪律。
- **分开之后要互相指**:每份的文件头写清「**本份不装什么、那在哪**」,否则下一个人找不到就会重抄一份。

> **这条是用来回答「怎么会有这么多份」的。** 份数多本身不是毛病——**说不出每一份为什么单独存在,才是毛病**。被问到时,**逐份把三轴答出来**:它多久变一次、谁能写、什么时候读。答不出来的那份,就是该合并的那份。

#### 角色的载体空了:**清空留壳,不要删**

⛔ **某个角色的条目全处理完了,把正文清掉、留文件头,但不要删那份文件。** 删掉之后,下一次同类产出**没有落点**;而需要落点的那个人**不会回头翻历史**——**他会另起一份新文件**,于是同一个角色有了两本书,两边各记一半。
> **同族**:v7.2 之所以要加验证反馈件,原因正是「验证方检查出 skill 问题」这个回路**在包里没有承接位置**;没有落点的产出不会消失,它只会落到一个没人约定的地方。
> ⭐ **v9.4 又验了一次同一条**:该角色原先只定义成「**站点**反馈件」,于是**还原测试**撞出的 skill 洞**也没有归位**——实际发生的是用户把那份文件改名成《验证发现的问题》、自己加了一节「还原测试回流」。**落点定得太窄,等于没定**:产出照样会来,只是来了之后没地方放。**定角色时问一句「还有谁会产出同一类东西?」**

> **对档案件尤其要紧**:它是**开窗必带件**,靠快照传播。一个每轮都变的必带件,意味着每个窗口手上的版本都不一样——**WF v6.5 撞号那件事的根因正是这个**,当时只修了计数器,没修「为什么计数器会在那儿」。
> **实证(2026-09-23)**:**档案件**一天内被改了九次;按本条收敛后**砍掉约三分之一,少掉的全是工单与副本**。

#### **档案件**装什么 · 不装什么

**档案件**顾名思义是**长期档案**,不是工单板,也不是一次性会话记录。它承载项目背景与目标、**当前基线(版本真值唯一位置)**、**阶段与里程碑**、协作指引、历史踩坑、已否决。**不留历史快照**,追溯看各资产自己的变更日志。

**⛔ 以下一律不进档案件**:

- **逐项待办与卡在哪** —— 归**在途件**(按线分段);本文件最多每条线一行「当前在做什么」,不展开细目。
- **进度看板每格状态**(某组件 📋→⏳→✅)—— 那是工单粒度。里程碑是「参考实现补齐」,不是每个组件走一格。
- **各资产的内容勘误与待补项** —— 归该资产自己(升版测试:改它要升该资产的版 → 就不归这儿)。
- **「已完成」流水** —— **那是各资产 `CHANGELOG.md` 的副本**。实证:2026-09-23 删除该节时实测 35 行里工作流包相关的逐条内容全在包内 `CHANGELOG.md` v6.0–v6.6,**是第三份副本不是唯一来源**。本文件只留一张「想查什么去哪查」的指向表。
- **任何包的字节数 / MD5 / 内容指纹** —— 校验值属于**某一次投递**,写进长期档案只会沉淀出过期值。**它们有专门的归宿——校验台账(§7.4)。**
- **计数器类的值**(如「下一个可用 EXEC 编号」)—— 靠快照传播的东西防不住并发,详见 `multi-window.md` §9。

**状态符号**沿用全局标注(✅/⏳/📋/🗂️/⏸️),**不得把未经过对应确认 / 发布条件的事项提前标 ✅**。

#### 活动件的文件名与引用

⭐ **每份活动件都必须在文件头声明「谁能写」。** 不声明,默认就是「谁都能整篇重写」——而这个载体**只能整篇写回、后写覆盖先写、双方都收不到提示**(`multi-window.md` §8)。声明分两种,照抄其一:

| | 怎么声明 | 适用 |
|---|---|---|
| **单写入方** | 「**写入方:{某个窗口}**。其它窗口只读。」 | 能定到一个窗口的,一律用这种——**结构上就撞不了** |
| **多写入方** | 「**写入方:{谁}+{谁}。⛔ 只动自己那段、只加不删、写完复读。**」 | 确实要多方写的(如两条线共用的在途件) |

- **多写入方的必须按写入方分段**,段内是谁的就只有谁动;**要清别人段里的条目 → 先问那条线**,不自行清理。
- **⛔ 不许出现「没写谁能写」的活动件**。新建一份活动件时,**文件头第一件事就是写清写入方**。
- **「先核一次当前状态」怎么核**:**不必整篇重读**——**搜自己上次写的那几句,命中且逐字一致即说明没被改过**。活动件可能很大,每次全读代价高到让人干脆不核。
- **活动件也要控体积**:**已被取代、且从未落地的条目可合并成一条**,保留认件所需的关键值即可。体积失控的直接后果是「整篇写回」变得昂贵,然后就没人愿意按规矩写了。
  > **实证**:本项目的校验台账曾涨到约 40KB,一天内被整篇重写五次;按 §7.0 拆分 + 合并压缩后降到约 15KB。

> **为什么是结构问题不是记性问题**:靠「大家小心点」防不住——**两次事故都发生在多写入方、且没分段的文件上**(2026-11-04 工作流窗口往台账写的四处次日被整篇盖掉;更早一次见**验证反馈件**第 3 条自述「此前台账曾记过同一条,现台账里已不见」)。**把写入方定下来、把段分开,是唯一不依赖记性的办法。**
> ⭐ **载体的并发能力实测(2026-11-06,v8.1 更正)**:**它会挡住「基于过期版本的整篇写回」**——签发方拿几分钟前读到的内容整篇写回时被**明确拒绝**,提示该文件已变、要求重新读取后再写;**另一条线同期写进去的内容因此没被盖掉**。
> **所以「静默覆盖」那个描述已经过期**(v8.0 之前写的是「没有锁、没有冲突提示、后写静默覆盖先写」)。**但三条纪律一条都不许撤**,因为它们防的是另一种撞法:

| 撞法 | 谁来挡 |
|---|---|
| **拿过期版本整篇写回** | ✅ **载体挡**(实测会拒绝)。做法:**被拒就重读一次再写**,别强写、别删了重建 |
| **同一份最新版本上,我重排 / 清理掉了别人的段** | ⛔ **载体挡不住**——我读的是最新版,写回也合法。**只能靠「只动自己那段 · 只加不删」** |
| **我以为写进去了,其实没有** | ⛔ 载体不会告诉你。**只能靠「写完复读自己刚写的那几处」** |

> ⚠️ **这条结论有保质期,且只对实测过的那个载体成立**(同类坑:包里曾把「本容器缺 rsync」当长期事实)。**换了载体重新测一次**:拿旧版本整篇写回,看它是拒绝还是静默接受。

- **文件名可以带版本号**(如 `国金DS常驻-项目总览_v1.3.md`),**只用来分辨手上是哪一份**,每改一次升一位;版本真值仍只记在该文件自己的「当前基线」一处。
- **⛔ 引用一律写书名**(**档案件**),**不写版本号、也不写路径**。带版本号意味着**文件名每升一位就变**,写死路径的地方必然失配。
- **不留历史快照**:旧版不归档、不另存,追溯看各资产的 `CHANGELOG.md`。
  > **若该载体靠「文件名带版本号」区分新旧**,那就**写了新版把旧版删掉**——不删就是两份并存,下一个窗口不知道该读哪个。**载体本身带版本管理时(能原地更新、能看历史)这条不适用**,别为了守规则去手工造冗余。
- ⚠️ **写活动件的工具限制(实测)**:`project_write` **只能读工作目录里的文件**——要从别处上传,先把文件拷进工作目录再写。另外它**只能整篇写回、没有逐条补丁**,所以必须守 `multi-window.md` §8 那三条(写时重读 / 只加不删 / 写完复读)。
- > 原先规定「活动件不带版本号」,理由是怕各窗口手上的快照对不上。实测反了:**带上版本号反而一眼看得出谁手上是旧的**(用户 2026-10-22 裁定)。
### 7.1 不重复原则 —— 同一内容只出现一次

> **这是本包的第一性规则,其余各条都是它在某个载体上的具体化。**

**同一条内容,整套里只写一处,别处只留指向。** 重复的代价永远是双份:写的人写一遍、读的人读一遍;而且两处措辞必然反向漂移,漂移之后没人知道该信哪个。

**它跨载体生效,不只管文件与文件之间。** 下面每一对都适用:

| 载体对 | 违反的样子 |
|---|---|
| **档案件**↔ 本包 | 踩坑表「改法」栏重抄规则正文 |
| 任务卡 ↔ `execution-standard.md` | 卡里重写 §六 的常规验证项 |
| 转交复制框 ↔ 卡 / 附件 | 框里放一段「要点」,摘要文件里已有的内容 |
| 执行反馈 ↔ 任务卡 | 反馈里重述卡文 |
| 续轮开场白 ↔ 规则文件 | 续轮重抄一遍规则 |
| 资产 `CHANGELOG` ↔ 资产 `references/` | 更新记录里把规则正文整段抄一遍,而不是指向该规则所在章节 |
| 参考实现的展示模块 ↔ 主预览 | 主预览已能覆盖 0–100%,旁边又摆一组边界状态卡片 |
| 收方复读 Figma ↔ 分出去的线已直读的真值 | 对方已直读、效果确认也过了,收方入库前再读一遍同一节点 |

**通用判据就是下面的删除测试**,换个对象用:**把这段话删掉之后,对方照他手上已有的东西做,还能不能做对?能 → 删。**

> ⚠️ **「怕他不看」不是保留副本的理由。** 对方不看指向,是指向写得不够准(没点到文件 + 章号),补准指向;不是再抄一份。

#### 内容归哪边 —— 三条测试

**档案件**是包外活动件。**某条内容该进本包还是进它,按这三条判,别靠直觉**:

| # | 测试 | 判定 |
|---|---|---|
| **1 · 升版测试** | 改这条内容,**需不需要升本包版本**? | 需要 → 归包;不需要 → 归**档案件** |
| **2 · 删除测试** | 把**档案件**里某句删掉后,**还能靠指向找到完整规则吗**? | 不能 → **包里缺这条规则,该来补包**,不是塞进活动件 |
| **3 · 时序测试** | 用户需要在**打开包之前**知道吗? | 是 → **必须在包外**(如「开窗要带什么」);否 → 归包 |

**三条都过不了就别写。**

> **⚠️ 测试2 是报警器,不是筛子**:活动件里反复出现「有现象、没规则可指」的条目(例如收尾核对连报三轮同一个偏差),那是**包里缺章节**在报警,应当来补包,而不是在活动件里攒。
> **档案件「踩坑表」的书写纪律**:「改法」栏只写**要点 + 指向本包条号**,不重抄规则正文——抄进去就是第二处副本。
> **活动件不写自己的校验值**:**档案件**正文里不写它自己的大小 / MD5,写了每改一次就失效;要核它,权威值写在当轮任务卡里。

### 7.2 本机镜像 —— 按需同步,**旧了不算待办**

**权威副本在 `{权威副本位置}`;本机若另有一份,它是镜像,不是真值。** 镜像给**够得到本机的窗口**就近读,同步时机:

- 要开有本地访问的窗口之前;
- 阶段性收尾(如包升版落地)顺带一起;
- 用户明确要求时。

> 判据:**没人要读它的时候,镜像旧着不影响任何人**。够不到本机的窗口直接取权威副本,不经镜像。

⛔ **镜像落后不算待办**:**不列进在途件、不出任务卡、不在交付里催**。只有「这一轮确实要读本机那份」时才就地同步一次。
> **实证**:本项目的镜像落后状态被当成待办挂了好几轮,还为它走过一整轮出卡 → 转交 → 执行 → 反馈,而那一轮的主要内容就是把几个目录挪进归档位。**追镜像不产出任何价值,它只是让副本追上真值。**

### 7.3 其它维护规则

- **进度看板不进本包,也不进档案件**:逐格推进状态是**工单粒度**,归**在途件**(按线分段,§7.0)。
- **任何跨轮才用得到的产出,当轮必须落到持久载体上。** 总则3「签发后的归宿是 Project 文件」只管**包**;脚本、草案、半成品这些**既不是包、也进不了 Project 文件**(那儿只收二进制),就会掉进缝里。**默认归宿是 Project 文档**,并在文档开头注明它是中转件、落进资产后要删掉。**半成品同理**——做到一半卡住了,当轮把「做到哪、卡在哪、重做时哪些能复用」写进活动件,别只留在窗口里。
  > **实证**:v6.7 / v6.8 丢的是包(规则层已在 v6.9 修)。2026-10-27 交付的 `check-update.sh` 差点重演——它只活在临时容器与聊天附件里,容器一重置就没,台账里那条待办就成了指着空气的一句话。**同一个坑的第三次,前两次丢的是包,这次差点丢的是脚本。**
  > ⭐ **出口:体积大到会挤占读取的产出(整页 HTML、内嵌字体的大文件…),可以只存在压缩件里**,但**必须在持久载体上登记三样:它在哪 · 怎么取 · 校验值多少**。**登记了才算落地,没登记不算。**
  > **为什么要给出口**:规则不给出口,执行者就自己造一条。**实测 2026-11-09**:56KB 的内嵌字体 HTML 只进了 zip、没进任何持久载体,窗口自己也知道这违背本条,于是在它自己的参数表里写了一条「大体积 HTML 只随 zip」的**私规则**——**私规则换个窗口就没了**。
- ⭐ **交接件里的「操作窍门」是待归属的知识,不是过程件——分流完才能删那份交接件。**窗口交接文档通常标着「新窗口核过即可删除」,而它的「操作窍门」一节恰恰装着**踩出来的、换窗口必丢的经验**。**删之前逐条分流**,按 §7.1 三条测试判:
  - **与具体设计系统无关的工具 / 过程纪律** → 本包(如 Figma MCP 的返回值上限、活动件的写入限制);
  - **依赖某个资产自己的文件** → 那个资产的包(如某组件编码去哪查、某份参考实现的样式怎么摘);
  - **项目专有的数据与配置** → 包外活动件(如 Figma 文件 key、下游 agent 的口令、工作区根路径);
  - **已经在某处写着的** → 删掉,别留第二份。
  > **验法**:分流完问一句「**这条现在写在哪?**」——答不出确切位置,就还不能删那份交接件。同族于 `multi-window.md` §8「下沉 / 移交规则先找承接位置」,区别是那条管规则、这条管经验。
  > **为什么要单写**:这类知识的默认命运是**随交接件一起被删**,而且删的时候没人觉得丢了东西——它看起来只是「上一个窗口的笔记」。

### 7.4 校验值与在途——两份分开的包外活动件

**校验台账**

| 项 | 内容 |
|---|---|
| **管什么** | 每个**已签发**包的 zip 字节数 / MD5 / **内容指纹** + 本版核验状态 |
| **谁写** | 该版的**签发方**,**出包当轮登记** |
| **何时读** | 用户回传 skill 包、需要确认「手上这份是哪一版」时 |
| **⛔ 不装什么** | **改动细节**(在该资产的 `CHANGELOG.md`,台账只写「见 CHANGELOG vX.Y.Z」+ 一行要点);**在途待办与口径**(在在途件) |

**台账为什么单设一份**:校验值**从包里推不出来**,任务卡用完即弃,而**档案件**按 7.0 不记校验值。**三者各有不记的理由,所以需要一个专门记的地方。**
**四者的分工**:档案件记**版本号**,校验台账记**校验值**,CHANGELOG 记**改动内容**,在途件记**现在卡在哪**——互不重叠。

⛔ **出包当轮要同步的是两处,不是一处**:

| 同步哪儿 | 记什么 |
|---|---|
| **① 校验台账** | 本版的字节数 / MD5 / **内容指纹** + 核验状态 |
| **② 在途件的本线基线行** | **现在该传哪个包**;并把上一版标成「已被取代、不必传」 |

> **为什么两处都要**:台账记「**是哪一版**」,在途件记「**现在该传哪个**」——**两件事**。而台账是**触发才读**、在途件是**开工前必读**,**漏了后者,错的那条就躺在读得最多的那份里**。
> **实证(2026-11-09)**:WF v9.2 / v9.3 / v9.4 **每版都登记了台账**,但在途件的基线行**连续三版停在 v9.1**,白纸黑字写着「只传 v9.1 这一个包」——**照它做会传错包**。根因不是忘性:**规则只钉住了台账那一处。**
> **通则**:**凡「当轮必做」的动作,包里要以清单形式列全**,别散落在各节靠人回忆拼。

**在途件**(实际书名见协作参数)

| 项 | 内容 |
|---|---|
| **管什么** | 两条线的**在途待办**、发布面与站点的**现状与口径**、有时效的待处理项 |
| **谁写** | **多写入方,按线分段**——各线只动自己那段,发布面谁动了谁写(§7.0 写入方声明) |
| **何时读** | **开工前**;要知道「现在卡在哪、发布面什么状态」时 |
| **⛔ 不装什么** | **校验值**(在台账)、**阶段与里程碑**(在**档案件**)、**改动细节**(在 CHANGELOG);⭐ **已完成项的清单**——在途件只装**还没完的事**,一条做完了就**只留一句「为什么它不再是待办」**,完整记录在该资产的 `CHANGELOG` 与校验台账 |
