# 国金DS · 设计系统制作工作流 · WF v11.2

> **本包讲什么**:维护「国金证券客户端设计系统 skill」的**过程规则**——这件事怎么干、谁在哪个窗口干、文件放哪、执行端怎么动手。
> **不讲什么**:设计系统的真值(token / 组件 / 场景)。那是**操作对象**,在 DS skill 里,经其 `SKILL.md` 路由按需读。
> **不发给谁**:不打包进设计系统 skill、不发给原型制作者。

> **文档分层**:本包是**项目层**,与用户个人使用习惯文件(通用层·跨项目·独立版本线,如有)配套。
> **冲突优先级**:**用户当轮明确指令 > 工作流包 > 个人使用习惯文件**。
> 「工作流包」指本包全部内容——`SKILL.md` 与各 `references/` **同一档**,包内不再分档。包内若出现互相矛盾的写法,按 §1 总则0 裁断,并报回修订,不靠档位压制。
> 本包**自包含**,不引用通用层条号(通用层不在本项目掌控内,其版本与章节号随时可能变);少量重叠属合理冗余,不据此删条。
> **新规则归属**:换项目仍成立且通用层可改 → 通用层;否则一律就近收进本包。**不为任何新规则派生包外新文件。**

> **本包版本线**:自 WF v6.0 起统一为**一条**。v6.0 之前是四条独立版本线(制作工作流 / 多窗口协同 / 工作区结构 / 执行端作业规范),旧编号仅供回溯,见 `CHANGELOG.md`「附、并入前的四条版本线」。正文与踩坑记录里出现的 `v1.4`、`v1.10` 等指的是那些线上的编号。

## §0 每轮操作卡

> ⚡ **照此线性执行。只写动作与去处;细则一律在被指向的章节,本卡不复述。**
> ⛔ **「被指向的章节」= 只读被点到的那一节,不是整份读那个文件。** 下表每一处 `process.md §X` 都带了节号——**照节号读;没点到的节不要读**(§7.0「读取时机」轴)。
> ⛔ **本卡覆盖的是「做 / 改一个组件」那种轮次**(步1–5 是它的主干)。**其它轮次不走本卡,直接按 §4 路由表去对应章节**——
> **改本包自己** → §2 总则3 + `process.md` 总则3.3-细则 + §7(改完按 `multi-window.md` §8 收尾);**对账 / 发布** → `process.md` §4.3 / §4.5;**纯答疑、纯核查** → 不出产物,只守 §2 总则4 与 `process.md` §6。
> **这三件对任何轮次都适用,别因为不走本卡就跳掉**:开工先过 §3.0(参数未定时)· 碰本地的事按 §3.3 三分支判 · present 前过 `process.md` §6 自检与交付节制。
> 🔄 **开跑前的升级自检:必跑一次;跑不了不阻断**(「不阻断」说的是**失败**,不是「可以不跑」)。有 bash 就 `bash scripts/check-update.sh`——输出含「已更新到」→ 告知用户已升到 v{版本},**重读本 SKILL.md 再继续**;其它输出 / 无输出 / 无 bash → 直接往下走。机制与硬闸门见 `process.md` §4.6。
> ⚠️ **只有一种情况要先断开再跑**:**分发方的仓里那一版可能比你手上这份新**(刚从别人那儿拿到包、而对方的仓还在维护)。那时先定 `{发布仓}`,或 `export GJDS_UPDATE_REPO=none`。**仓里不比你新 → 脚本静默退出,照常跑就行**(实证 2026-11-09:仓 `workflow/VERSION=6.12`、手上 9.4,脚本 `is_newer || exit 0` 直接退出)。

### 入口 —— 用户第一句话是什么,决定你先做什么

| 用户给的 | 你先做什么 |
|---|---|
| ⭐ **一句工作指令 + 真值位置**(「现在开始做理财业务组件,Figma 链接 xxx」)——**最常见的真实入口** | 走下面「**零仪式启动**」,**四步做完再回话**。⛔ **不要先问一轮参数再开工** |
| ⭐ **一张已经做好的页面 / 整份设计稿**(「把这个页面按组件拆一下」「这稿里哪些要做」) | 仍走零仪式启动;**但在步1 之前先插一段 `process.md` §4.10 把稿拆开**,拍板之后,要新做的组件再各自走步1–9 |
| 明确的流程指令(改包 / 对账 / 发布 / 纯答疑) | 不走本卡,按 **§4 路由表**直接去对应章节 |
| 额外约束、交接上下文 | 照它说的办;其余仍走零仪式启动 |

#### 零仪式启动(收到工作指令后、**回第一句话之前**做完)

| | 做什么 | 依据 |
|---|---|---|
| ① | **读包**:本卡 + §2 七律 + §3.3;再读**被维护 skill 的入口**。**不用人说「先读」**。⛔ **`process.md` 不要整份读**——本步只读它的 **§4.1**(直读真值)与 **§6**(输出前自检);其余各节**等触发的那一刻再读**(§7.0「读取时机」轴) | §2 总则1 |
| ② | **自测环境**:够不够得到本机 · **写得进哪儿** · 读不读得了真值 · 能不能出图。⛔ **一项都不许假设** | §3.3 ① · §3.0 |
| ③ | **自己把载体建起来**:按 §3.0 的默认值建——**写得进项目 / 知识库就写那儿,只能写本地就写本地,都不行就把内容直接给用户**。⛔ **建载体不用先问** | §3.0 |

> ⛔ **「建载体」与「开始做」两道闸门不一样**:建文件**可逆、低风险 → 直接做**;**真正动手做第一个组件要用户点头**(要读真值、要渲染、而且定了方向)。

> ⛔ **回话里不要复述规则**。用户要看的是**你做了什么、还缺什么**,不是本包有哪些条款。

## §1 总则0 · 冲突裁断与优先级

规则冲突时按此裁——

- **① 质量底线不可降级**:事实源唯一(总则1)、两次确认(总则4)、只用 Figma 直读真值不猜(`process.md` §4.1)、版本贯穿(总则3)、影响自升级机制的改动必经用户重点确认(`process.md` §4.6),**不因用户催促或赶进度而跳过**。
- **② 节奏 / 产物选择听用户当轮**:"出不出校验图、发不发某复制框、走 inline 还是 HTML、先做哪个组件"这类**默认动作**,以用户当轮明确指令为准。本包的默认动作是"无人指示时怎么做",**不是用来拦住用户**。
- **③ 二者冲突**:底线优先于催促;不破底线的前提下,用户明确指令优先于本包的默认动作。

> **统一标注符号(全产出适用)**:🚧=需用户确认 · ⚠️=有问题/偏差 · 📋=短期待办 · 🗂️=长期待办 · 📎=附件/随附内容。

## §2 七律(全员、全程适用)

### 总则1 · 设计真值在 Figma;DS skill 是固化而来的 AI 执行载体

**设计真值的唯一来源是 `{设计真值来源}`**——哪个工具、哪个文件 / 库,**开工时问一次并记在项目侧**(§3.0)。本包的取值、写回与校验流程(§4.1 / §4.7)是按 **Figma** 写的;若换成别的设计工具,**那两节要跟着适配,别假装工具无关**。**DS skill 不是设计真值的源头**,它是把 Figma 的真值**固化成 AI 可执行形式**的载体——除了数值,还装着专为 AI 生成写的规则(场景、限制、组合约束)。

**改动顺序:Figma → skill → 站。** ⛔ **但「反向」不是一刀切——分三种,走法完全不同**(v8.1 修;原文写成「站 → skill 与 skill → Figma 一律不走」,把总则2 情况2 与 §4.7 两条现行机制都否掉了):

| 反向的方向 | 走不走 |
|---|---|
| **站 → 设计真值** | ⛔ **一律不走。** 展示 / 发布层只动表现与文件名,绝不反向改真值 |
| **站 → skill 的表述** | ✅ **要走。** 站照 skill 做不出来 / 做出来不对 / skill 两处矛盾 → 那是 skill 的洞,**回来改 skill**(总则2 第二层情况2)。改的是 **skill 对规则的表述与它自己的参考实现**,设计真值一个字没动 |
| **skill → Figma** | 🚧 **要走,但是硬闸门。** 把已固化真值写回 Figma 组件属正常流程,**须用户显式同意才动**(`process.md` §4.7) |

**一句话**:**不许反向改的是「真值」,不是「表述」**。

- **skill 有、Figma 没有的内容:正常,保留在 skill。** 那是为 AI 生成补的规则,比 Figma 多属预期,**不算冲突,不必等 Figma 补**。「以 Figma 为准」**只管两边都有、且数值或样式不一致的情况**。
- **Figma 自身前后不一致**(同一组件在不同页面数值不同):**报给用户,由用户决定**。AI **不自行择一**;定了再改 Figma 或改 skill。
  > ⛔ **报之前先截图确认**——看一眼它实际长什么样,再说「Figma 有问题」。**坐标类判断尤其要注意是相对哪一层**:metadata 里的 x / y 是相对父层的,`absoluteBoundingBox` 才是相对画板的。
  > **实证**:2026-11-05 C12 图标宫格,读到分页符 `y=120` 就报「分页符压在第二行上」,用户追问后截图一看位置完全正常——`y=120` 是相对内层容器的。**报错门槛低了,用户就会被拉去看一个不存在的问题。**

**事实源在文件、不在对话**——这条不变,同样适用于本包:窗口卡死就弃掉重开,损失为零(`multi-window.md` §4)。

> **2026-10-23 改口径**:原文是「唯一事实源在设计系统 skill」。用户原话——「经过一段时间的与研发的联调,AI 与 Figma 的畅通程度越来越高,决定最终都以 Figma 的内容为准」。**旧措辞在全包多处出现过,本版已逐处改写**(本页 §3.1 与 §3.4;`process.md` §4.1 与 §4.3;`multi-window.md` §1 与 §6;`workspace.md` 的目录树注释)。

### 总则2 · 差异分两层裁决(第二层双向)

| 不一致发生在 | 以谁为准 | 改谁 |
|---|---|---|
| **Figma ↔ skill** | **Figma** | 改 skill(总则1) |
| **第二层** · skill ↔ **验证方**:**两种情况都存在,逐条判,不预设哪个是默认** | 见下 | 见下 |
| ├ **情况1** · skill 写的是对的,**验证方做错了** | **skill** | **改验证方那边** |
| └ **情况2** · 验证方**检查出了 skill 的问题** | **验证方的发现** | **改 skill** |

⭐ **「验证方」指任何照 skill 亲手做东西的一方**:做展示站、用 skill 还原设计稿、别的窗口照 skill 产出页面……**都算**。v9.4 之前这一层只写了「站」,于是**还原测试撞出来的 skill 洞在包里没有归位**。

skill 对验证方而言是**上游**,不是「设计真值的源头」——两件事别混。

⛔ **第二层不要套公式判。** 情况1 与情况2 **都真实存在,而且常常同时存在**——所以**没有一条判据能把每条差异自动归位**,只能**逐条看**。下面是**判断时该看什么**,不是判据公式:

**往「情况1(验证方做错了)」靠的迹象**:它用的值 / 资产 skill 里根本没写过(自己发挥);skill 那一段**只读文字就能唯一画出来**,它却做成了别的;它拿的是旧版 skill(先核版本戳,见下)。

**往「情况2(改 skill)」靠的迹象**:只读 skill 那段文字**画不出来或会发散**(缺数值 / 状态没说清 / 资产没钉到该层精度);skill **两处自相矛盾**,验证方只能挑一个;参考实现**按闸门 A2 摘进页面就失效**;**规则没覆盖它真撞到的那种情况**;**换个人照着做大概也会做错**——那就是规则的问题,不是这一次手滑。

**⚠️ 允许「两边都要改」,这不是例外、是常见情况。** 验证方先在自己这边绕过去让产物能看,**同时** skill 侧记一条待修——两件事都要做,**别因为那边已经不报错了就把 skill 的洞划掉**。

**⛔ 判不了、或两边都说得通 → 列出来交用户拍板,不自行择一。** 这与总则2 第一层「Figma 自身前后不一致就报给用户」同一条纪律:**裁决权在用户,AI 只负责把两种可能摆清楚**(各给现象 + 实测数据 + 各自的代价)。

⛔ **情况2 不是「反向改真值」**:设计真值在 Figma、一个字没动;改的是 **skill 对规则的表述与它自己的参考实现**。

> **为什么要单列**:**照 skill 亲手做一遍东西,是唯一能验出 skill 起不起效的方式**(§3.1)——只读 skill 看不出它哪里写不全。验证方会**成批撞出 skill 的洞**,而这些洞**在别的地方撞不到**。只有「改验证方那边」这一个方向时,它们会被当成验证方自己的 bug 退回去,**而 skill 里那个洞还在**。
> ⚠️ **v9.4 更正**:原文写「站点是目前**唯一**会完整消费 skill 的下游」——**那句已经不成立**:用 skill **还原 Figma 设计稿**同样完整消费它,2026-11-09 的还原测试就撞出三条规则缺口(库外图怎么导、稿内裸色怎么办、闸门 B 只比模块高度漏掉局部形状)。**「唯一」这类话最容易过期,别写。**
> **实证(来自两个不同的验证方,都落在同一份**验证反馈件**里)**:
> · **站点验证**那 3 条都偏情况2——演示框高度没给边框留位导致分页符被裁、同一个槽的透明度 skill 内部两处不一致、参考实现用小写 token 别名导致「摘样式进页面」后选中态失效且深色模式切不过去。
> · **还原测试**那 3 条也都偏情况2——库外图从整页截图裁会带走稿内底色(规则只写「从设计稿导出」没说怎么导)、稿内裸色不在 token 表也没绑变量时规则没说能不能直写、闸门 B 只比模块高度与整段缩略图而漏掉局部异形。
> **都不是验证方做错了,是照着做才暴露出来的。**
> **而第三条正好也是「两边都要改」的实证**:站点本轮已在站点侧改用大写语义 token(属站点自己的适配),**skill 侧那条仍然待改**。若按「二选一」判,这条很容易被当成「站点已解决」而把 skill 的洞留在原地。

### 总则3 · 版本与命名

**3.1 版本签发**
CHANGELOG 用语义化 `主.次.修`,是唯一签发源。档位判定按优先级:**① 破坏性变更(最高):token 值、基准、取用顺序等影响既有产物兼容性的 → 主版本位;② 结构性重构 → 主版本位;③ 新增组件/章节 → 次版本位;④ 改细节/勘误 → 修订位**。
设计系统与本工作流版本号**各自独立签发**;**跨资产引用一律带前缀**(DS=设计系统 / WF=工作流,如 `DS v3.29.7`、`WF v6.9`;**各资产当前版本真值一律查「档案件」的「当前基线」节**,本行只示范写法)。

> **⛔ 签发之后,包的归宿是 `{权威副本位置}`,不是本机副本。** 实际值见项目侧「协作参数」(§3.0)。
> present 只是给到用户;**包要能被下一个窗口读到,得进 `{权威副本位置}`**。
> ⚠️ **一轮改完落地一次;轮内的中间版本不催、不传。** 一次优化里可能连出好几版(后一版把前一版整个含进去),**只在用户说这一轮完了、或他主动要时才提落地**。
> > **实证**:2026-11-06 一天连签 6 版,其中 5 版当天即被取代,**却每版都催了一次上传**——纯浪费。本条的要防的是「一轮的终点没落地」,**不是「每出一版都催」**。
> ⚠️ **落地这一步可能只有用户能做**:若 `{权威副本位置}` 是签发方写不进去的地方,就得用户自己搬。**够不到就按 §3.3 分支③ 说清,别假装能做。**
> > **实测(本项目当前载体)**:Project 的**文档**与**文件**是两套存储——签发方能读写的只有**文档**(纯文本),而**包属于文件(blob),工具侧没有写入口**;`content` 与 `local_path` 两种传法**均实测拒绝**(报 `project docs cannot store NUL bytes`)。**结论是试出来的,别再试第三遍;但换了载体要重新试。**
> **因此:出包**不**默认配一张任务卡。** 只有当本轮确实要动**用户本机的工作区**(归档旧目录、同步别的 agent 的挂载副本、整理 `历史文件/`)时,才按 §3.3 判分支——**本窗口够得到就自己做(②),够不到才出卡(③b)**;只换包不动本机的,**进 `{权威副本位置}` 就算到位**。
> **实证**:WF v6.7、v6.8 连续两版签发后**都没落地**——任务卡没发,包只到下载夹,权威副本停在 v6.6,两版就此蒸发,改动要重做。**根因是签发后没有持久归宿,而不是谁忘了。**

> **⛔「签发」以 present 为界,不以落地为界**:包一经交给用户(present / 发出),**该版本号即冻结**;此后任何内容改动——哪怕只改一个字、哪怕用户还没下载、哪怕还没进 `meta/`——都必须**升位重发**,不得沿用同一版本号。
> **理由**:发出去的那一刻你就失去控制了——用户可能已下载、执行端可能已解压、它可能已进本机镜像。版本号的唯一用处就是在这种时候分辨"这是哪一份",而"还没落地所以不算数"恰恰在最需要它的时候把它冻住。
> **同族**:与「任务卡一经 present 即视为定稿,要改就换卡号重发」是同一条(见 `assets/templates/exec-card.md` §二)。
> **配套 · 每次 present 包必须给出「包内容指纹」**(算法见下),**zip 的字节数与 MD5 同时给,但只作辅助**;**签发当轮同时登记进校验台账**(`process.md` §7.4)——指纹算得出来、却从包里推不出来,不登记就没人能回头确认手上是哪一份。
> **⛔ 权威钉在内容上,不钉在压缩容器上。** zip 是信封:用户的系统把它自动解开再压回去(macOS Safari 下载后自动展开 + Finder 重新 Compress,会塞进 `__MACOSX/._*`),**内容一字未改而容器 MD5 全变**。拿容器值当权威,下游会把一个完全正确的包判成「不命中」而整卡停下——**白跑一轮,且错的是判据不是包**。
> **实证**:WF v6.5 present 后,用户手上出现 91663 / `0ff7f885…` 的同内容副本(签发件为 83728 / `9ccd640a…`),包内 `SKILL.md` 与 `execution-standard.md` 的 MD5 两份完全一致。
> 本条源于 WF v6.1,v6.6 把权威从容器改到内容,详见 `CHANGELOG.md`。

#### 包内容指纹 —— 算法(照抄,别自创)

对**解压后的包顶层目录**:

1. 列出其下全部普通文件的**相对路径**(相对该顶层目录),**排除系统文件**(`.DS_Store`、`._*`、`__MACOSX/` 下的一切);
2. 用 `LC_ALL=C` 排序;
3. 每个文件输出一行 `{相对路径}` + 两个空格 + `{该文件 MD5}`;
4. 把这份清单文本(含每行末尾换行)整体取 MD5,**即为包内容指纹**。

```bash
# 在包顶层目录内执行。macOS 用 md5 -q,Linux 用 md5sum。
find . -type f ! -name '.DS_Store' ! -name '._*' ! -path './__MACOSX/*' \
  | sed 's|^\./||' | LC_ALL=C sort \
  | while IFS= read -r f; do echo "$f  $(md5 -q "$f" 2>/dev/null || md5sum "$f" | cut -d' ' -f1)"; done \
  | tee /tmp/wf-manifest.txt | (md5 -q 2>/dev/null || md5sum | cut -d' ' -f1)
```

> 中间那份 `wf-manifest.txt` 本身就是诊断件:指纹不符时,**直接 diff 两份清单就知道是哪个文件不同**,不必逐个猜。

**3.2 每份输出物带版本号 —— 贯穿全员每一次输出物**
版本号由 skill 的 CHANGELOG 统一签发(3.1),**全员每一次输出物都要带**,不分角色、不分轮次:
Chat / Code 交付的每个文件(zip/md/css/html)文件名含版本号;每条 Design 提示词开头注版本号;Design 页面内每块内容标其对应版本号(照抄不自创),导出文件名带版本号。

> **⛔ 预览 / 草稿用轮次号 `r{n}`,不带资产版本号。** 轮次与版本号是**两套计数**。
> **判据**:这件东西**签发了吗**?签发了 → 版本号;还在等确认 → `r1`、`r2`…,文件名和标题都不带资产版本号。
> **实证**:骨架图前 3 轮预览内容各不相同、全标「v4.1.0」,用户问「版本号为什么没有迭代」。
> **同族**:与 v6.0「同一个版本号 present 了 5 次」是同一个病——**一个编号背了两种含义**。

**3.3 skill 包命名与上传合规 —— 三条硬约束(红线,违则传不上去、返工)**
1. **顶层目录名 + 全部内部文件 / 目录名一律纯 ASCII**(字母 / 数字 / `_` / `-`,无中文、无点号、无空格)。
2. **版本号存于 `VERSION` 文件 + `SKILL.md` 的 `metadata.version` + `CHANGELOG`**,**不作 frontmatter 顶层字段**。
   > ⛔ **这三处是 §7.1「同一内容只写一处」的唯一例外,所以必须配机械断言**:`metadata.version` 给载体读、`VERSION` 给自升级脚本读、`CHANGELOG` 是签发源——**三个读者互不相通,删掉任何一处都有人读不到**,因此只能留三份 + 每次出包核一遍。
   > **打包前必跑一次机械断言**(4 行 bash,照抄,别靠眼看)→ `process.md` 总则3.3-细则。
   > **实证(2026-11-06,本包自己栽的)**:v7.0–v8.0 **连续六版**的 `metadata.version` 与标题都停在 `6.12`,而 `VERSION` 与 `CHANGELOG` 是对的。**漏网原因是自升级只核 `VERSION` 文件**——规则写着「三处一致」却没有任何一步去核它,于是「写三处」只落实了一处。**有副本就必须有断言,否则副本一定漂。**
3. **`SKILL.md` frontmatter 仅用合规字段**:`name`(kebab-case 纯小写)、`description`(触发词并入其末尾)、`metadata`(version / slug / maturity 等自定义字段收纳此处;**不放 baseline 之类的他方版本号**——版本真值只记**档案件**的「当前基线」节一处,写进这里必过期。实证:本字段曾停在 `DS v3.29.7` 不动,而 DS 已到 v4.1.1)、及 license / allowed-tools / compatibility。`slug` / `version` / `maturity` / `triggers` 等**禁作 frontmatter 顶层字段**(否则 invalid_request_error)。

> 打包细则(目录名带版本的写法、`__MACOSX` 排除、validate.py 守卫、与自升级的关系)见 `process.md` 总则3.3-细则。

**3.4 设计系统 skill 双版交付(按需)**
**默认只出多文件路由版 zip**(主力·全面:三层架构基础规范 / 通用组件 / 业务场景,按 SKILL.md 路由);**单文件·基础规范精简版 `.md` 按需出**——仅当用户明确要分发 / 嵌入底座时再出(只含基础规范真值,文件头注范围并指向全面版)。需要时与 zip 同版本号;基础规范变动后若用户要单文件则同步内容。

**3.5 / 3.6**:站点(展示站)版本号规则、可视化站部署交付规范 → 见 `process.md` 总则3.5 / 总则3.6。它们是**阶段性动作**(打包、上线时才用),不是每轮动作,故不占本页。

> **目的**:任何产出物从 **VERSION / zip 文件名 / CHANGELOG** 即可溯源版本;且 skill 包随时可直接上传 Claude.ai Skill,**不因命名返工**。

### 总则4 · 用户确认才算完成 · 两次确认,Chat 不自行宣布完成

每个组件 / 维度必走两次确认——
- **效果确认(数值与效果)**:过了才写进 skill;
- **文本确认(表述与归属,可抽查)**:过了才打包 / 升 SKILL 版本 / 回写看板 ✅。

**🖼️ 要用户确认或拍板的东西,必须让他看得懂。** 凡需用户**判断**(待确认项、Figma 疑点、方案取舍)或要**指给他看某一处**(文件里的某段、组件的某个部位),**默认配一张说明图**——截图、标注位置、对比图;**纯文字只用来下结论**。

**⚠️ 本包里「图」有两个意思,别混**:

| | **校验图 / 渲染图** | **说明图** |
|---|---|---|
| 干什么用 | 让用户确认**数值与效果** | 让用户看懂**说的是哪儿** |
| 成本 | 高——要渲染、要真实有代表性的数据 | 低——截图、圈一下、列个对照表 |
| 什么时候发 | **只在**「用户须看效果拍板」时(`process.md` §6 自检9) | **需要判断或定位时,默认配** |

**旧条文里的「不出图 / 不出校验图」一律指校验图**,不是不许给说明图。
⛔ **「本窗口出不了图」是个要先证伪的说法,不是免责条款。** 走文字替代之前**先试一次**(截图工具 / 渲染一张 / 直接发文件),**试过确实不行**才用「**原文摘录 + 精确位置 + 表格对照**」代替,并注明**是哪个窗口、试了什么、怎么失败的**。
> 同 §3.3 分支① 一个道理:**不确定就先自测,别假设**。这条退路是给真出不了图的载体留的,**不是给懒得出图留的**——当初加它时确有窗口出不了图,现在多数窗口都能渲染、截图、直接发文件。
> **实证**:2026-10-27~28,C02 / C04 / C11 / C19 连着四个组件用纯文字描述组件,用户看不懂(「你这么写我根本不知道你说的是哪个组件」「没看懂,说的是哪儿」),补图后才推进——**四次本可以避免的往返**。
> **根因是「下沉没人接」**:个人习惯 v4.5 把「视觉交付」以「预设项目有视觉产出」为由下沉到项目层,而 WF 只接住了「效果确认出校验图」这一半,**「说明要配图」那一半两边都没有了**。维护侧的规则补在 `multi-window.md` §8。

待确认清单的拍板(规则、命名、缺态)是**确认前置**,**不替代**两次确认。渲染校验图后只能说"请确认效果";用户表态前不得写"已完成"、不标 ✅、**不打包、不升版本、不动看板**、不跳下一步。

**⭐ 短回复(「可以的」「继续」「按你推荐的来」)到底确认了什么 —— 按清单算,不按猜**

- **只确认「你上一条回话里明确列成编号 / 清单的那几项」。** 清单之外的事**一律不算确认**。
- ⛔ **你上一条没给出明确推荐,一句「按你推荐的来」就什么也没确认** —— 这时**把推荐补出来再问一次**,不许自己补一个解读往下走。
- 当轮回话里**写明一行「这句话我理解成:{X}」**,让用户一眼能纠。
> **实测(2026-11-09 冷启动)**:三次短回复**全靠猜、一次都没核实**;其中一次用户说「按你推荐的来」,而窗口上一条**根本没给过推荐**,它自己补了一个解读。

- **确认反馈三类**:① 确认通过 → 进下一步;② 指出问题 → 回该次确认改后重看;③ 缩范围 / 延期 → 更新本轮范围后继续。
- **⛔ 修改指令 ≠ 确认。** 「按你推荐的改」「照这个来」是**针对改之前的计划**下的指令;确认**针对改之后的结果**。**出包前要有一次针对「本版实际改了什么」的表态**,修订位也至少要一句。
  > **实证**:DS v4.0.2 在「按你推荐的改」之后直接打包签发,用户没见过改动清单,也没给内容指纹。
- **⛔ 出包前先核范围:工作副本 ≠ 本版该收的东西。** 打包前把工作副本与**上一签发版逐文件 diff**,每个差异文件都要能对到**「两轮确认都已通过」**的那个组件 / 条目;**对不上的不进包**,留在工作副本等它自己的确认。
- **⛔ 出包前跑一遍该包自己的校验脚本,并清掉脚本运行产生的缓存。** 缓存目录(`__pycache__` 这类)**会被打进包、让内容指纹变**,而它不是本版内容。**具体跑哪几个脚本看该包自己的说明**,本包不列名字(列了就得跟着那个包升版)。
  > **实证**:DS v5.1.0 首次打包把在途未确认的 C02–C06、C18、C19 与基础规范改动一并打进(132 个文件),是用户看改动清单时指出的;按「只收已确认」重打后是 109 个文件。
  > **为什么会漏**:工作副本是**连续**的,签发是**离散**的——不主动划线,打包就会把「写到现在为止的一切」当成本版。
- **轻量修订路径**:修订位(仅个别数值 / 措辞小改)走轻量——**只给文案确认、不出校验图**(除非用户要可视化);新增组件 / 章节仍走完整两次确认。**省掉的只是校验图**,说明图不在省的范围里(见上对照表)。

> **两次确认都是用户确认,不按角色分布**:效果确认(数值与效果)过了草案才成立,文本确认(表述与归属)过了才升版打包;**在哪个窗口做的活就在哪个窗口确认**——见 `multi-window.md` §1。

### 总则5 · 任务清单制(每轮必做)

用户每发一条消息,Chat 必须——开头把消息拆为编号任务(含隐含任务,如"修改后需同步 skill");交付前对照逐项核对;结尾每项标 ✅完成 / ⏳进行中(说明卡在哪)/ ❌未做(说明原因),**不静默丢弃任何一项**。

⭐ **单任务轮:可以不编号,但结尾那一行状态照写。**
> **为什么单独拎成一行**:这半句原先挂在上面长句的尾部,**读者看不见**。个人使用习惯文件里也有「单条任务不编号」——两者并不冲突,**真正会出事的是把「不编号」读成「这一轮不用报状态」**。实测(2026-11-09 冷启动):单任务轮既没编号、也没写状态行,窗口当时**没意识到两边有出入**。

### 总则6 · 凡要用户转交给下游的东西,一律配复制框

**适用于所有下游,不限于某一个**:Design、分支③里那个替你动手的 agent、别的窗口、备用 trae —— 只要**需要用户手动粘贴出去**,就得给复制框。

⛔ **前提是「真的要转交出去」。** 本条管的是**跨窗口搬运**:同一个窗口里自己接着做的事,**不需要给自己写提示词**(比如做完 skill 顺手在同窗口做站点)。**先判这一步要不要跨窗口,再决定要不要复制框。**

- 放入**复制框(代码块)整体输出**,便于一键复制;框内为**纯提示词正文**,不混入对用户的说明;说明写在框外。
- **⛔ 交付件 ≠ 提示词,两者都要给**:出了任务卡 md、参考实现文件、草案包,**不等于**完成交付——用户还需要一段话把它转交出去。**产出物与转交复制框必须同轮一起给**,不能只给文件让用户自己组织措辞。
- **各下游的复制框骨架在 `assets/templates/`**:任务卡 → `exec-card.md` §二;开场白 → `kickoff-brain.md` / `kickoff-branch.md`;Design → `design-prompt.md`;**交付包(你只出素材、要交给签发方时)→ `handoff-package.md`**。**照抄,不自创。**
  > ⛔ **「交给签发方入库」也是转交。** 只出素材的窗口交完 `交付说明.md` 与参考实现,**同轮要给转交复制框**——实测 2026-11-09 冷启动:整轮 17 次往返,**本条一次都没执行**,窗口事后才反应过来这条适用。

> **本条适用范围曾漏扩**:原文只写「Design(或备用 trae)」,写于项目里还没有「替你动手的执行端」这种下游之前;v5.7 真的多出这种下游时没回头扩这条,导致「发卡要不要连带给复制框」在规则里无处可查,实战中连续漏发。**新增下游 / 通道时,须回头扫一遍所有按旧下游集写死的条款**(同族坑见**档案件**的「踩坑表」)。

### 总则7 · 组件命名 —— 语法归被维护的 skill,本包只管两件事

⛔ **本包不复制命名语法。** 「族-形态-档位」怎么写、档位主键取什么、排布与场景的受控词表有哪些——**那是被维护 skill 自己的真值**(本项目:DS `SKILL.md` 的「命名与示意文案」总则 + `references/components.md` 文件头「命名引用」)。按 §7.1 升版测试:**改那套词表要升 DS 的版、不升本包的版**,所以它不归这儿。

> **实证(2026-11-06 实测,v9.0 据此删的)**:本包 v8.1 之前抄了一份,**而且已经漂了**——逐条核 DS v5.13.3 时发现**至少两项对不上**:**排布受控词表**(本包抄的是三个词,DS 现行不是那三个)与**基础业务域的子域名**(本包的举例在 DS 里已改名)。
> DS 自己的 `CHANGELOG` 记着旧词表正是本包抄的那一版——**DS 改过,本包没跟,而且没有任何机制会让它跟上**。
> ⛔ **这里故意不写 DS 现行的值是什么**:写了就又是第二处副本,下次照样漂。**要用就去读 DS 的入口。**

**本包只保留两条——都是协作纪律,不是命名真值:**

| | 规则 | 为什么归这儿 |
|---|---|---|
| **1** | **跨窗口、跨协作方引用组件,一律写全限定名**:任务卡、转交复制框、草案交回、改包建议、对账差异表里提到组件,**都要写到能唯一认出那一个变体**,不用裸档位、不用口头简称。 | 它管的是**两方之间怎么指同一个东西**,与具体语法无关;换个设计系统照样要守 |
| **2** | **命名与归属是规则,归提案 + 用户拍板**:新组件 / 新档位的名字、以及它算通用还是算某个场景专属,**先按被维护 skill 的语法提案,经用户确认后才随固化入库**;拿不准**不自行择一**(总则4)。 | 裁决权归属问题,与总则2 第一层同一条纪律 |

> **适用范围**(限定词,别拆掉):**全员**——本窗口、别的窗口、替你动手的 agent、做站的那方,一律适用,不分窗口、不分载体。
> **语法本身去哪查**:被维护 skill 的入口(本项目 DS `SKILL.md`)。**本包不转述、不举例、不列词表**——举一个例子就是第二处副本。

## §3 载体、通道与分支

### 3.0 开工自己定一次 —— 能定的自己定,定不了才问

⛔ **本包不假设任何项目专有的值。** 路径、权威副本在哪、设计真值在哪、谁签发、有没有发布面——**这些随人、随 agent、随软件版本变**,所以包里只写**要知道什么**,不写**答案是什么**。答案记在项目侧。

**什么时候做**:**一个新协作关系开始时做一次**(新人接手、换 agent、换载体),**不是每轮都做**。值已经记在项目侧 → **直接读,不要重做、更不要重问**。

⛔ **默认是「自己定」,不是「问用户」。** 下表七项里**绝大多数都能自测出来或有保守默认**;真正只有用户知道的,**他那句工作指令里往往已经给了**(要做什么、真值在哪)。**理想情况:一个问题都不用问。**

**先自测,别问**(能试出来的一律不占用户,见 §3.3 ①)。三项各有确切动作,**跑完把结果填进问话里**:

| 要自测的 | 怎么算测过 |
|---|---|
| **够不到用户本机吗** | 拿本机工具列一次目录(或读一个文件);**报错原文读完**——「没挂目录」与「没这个工具」处置不同 |
| **能不能出图** | **渲染一张最小图并确认自己看得到**:写一个几十字节的 HTML / SVG,用本窗口的渲染或截图能力出图,**自己 view 一次**。看得到 = 能出图;只能产出文件、自己看不到 = **不算能出图**(总则4 要的是「用户看得懂」,拿不回像素就配不了说明图) |
| **够不到权威副本吗** | 对 `{权威副本位置}` 跑一次**只读**取用;**读得到 ≠ 写得进**,写入要另测(实证见总则3.1) |

**七项逐项:先看能不能自己定**

| | 要知道 | **自己怎么定** | 定不了才问 |
|---|---|---|---|
| 1 | **设计真值在哪** | **用户那句工作指令里通常已经给了**(链接 / 文件名)。给了就直接用,**别再问一遍** | 一个字没提才问 |
| 2 | **权威副本在哪** | **自测写得进哪儿**:写得进项目 / 知识库 → 就是它;只写得了本机 → 就是本机目录;**都写不进 → 内容直接给用户,由他放** | 两处都写得进、不知道该用哪个时才问 |
| 3 | **路径**(仅当要碰本机) | **自测列一次目录**就知道够不够得到、根在哪 | 够得到但不知道该用哪个目录时才问 |
| 4 | **谁签发** | **默认:本窗口就是唯一签发方**(§3.1)。⚠️ **本项只定「这条线归谁签」**;「本窗口是签发方还是只出素材」在**第6项**判,别在这儿判 | 用户提到还有别的窗口 / 别人在改同一份,才问怎么分 |
| 5 | **有没有对外发布面**(仓 / 站点) | **默认:没有** → **§4.9 整节不适用**,不提推仓、打 tag、部署 | 用户提到仓 / 站点时才问三个值:`{发布仓}`(仓名 / 分支)、`{站点}`、`{本包在仓里的子目录}`。⛔ 这三个同时是**自升级的版本源**(`process.md` §4.6) |
| 6 | **协作形态** —— **本窗口是签发方,还是只出素材?** | **默认:本窗口唯一、且自己签发** → 不出任务卡、不发转接件 | 用户提到别的窗口 / 外援 agent,**或说「你只出素材、不改包、不升版」**时才问 |
| 7 | **确认与汇报习惯** | **默认:按本包**——两次确认 + 要用户判断的配说明图(总则4) | **不问**。用户表达过偏好之后再记进参数件 |

> ⭐ **协作形态有三种,第三种最常见、也最容易被漏掉**:
>
> | 形态 | 这一路的终点是什么 | 走哪条 |
> |---|---|---|
> | **本窗口就是签发方**(默认) | 打包 / 升版 / 登台账 | 操作卡**步6** |
> | **把活分给别的窗口做** | 收对方交回来的交付包,自己验、自己写库 | `multi-window.md` §5(**收方**那一侧) |
> | ⭐ **本窗口只出素材、不签发** | **交一份 `交付说明.md` 给签发方** | 操作卡**步6′**(它再指 §5 与模板) |
>
> ⛔ **第三种不是「包里没规则」——规则就是 `multi-window.md` §5 的那七项。** 别因为那一节从前叫「别的窗口交回来的东西」就以为它只写给收方:**你交出去的那一份,要的就是那七项。**

⛔ **按默认走可以,但必须在回话里一句话标出来——不许沉默假设。** 写法:「{这几项}我按默认处理了:…;不对你说一声。」
**为什么要标**:默认会让你少做事(不碰本机、不提发布),这通常是对的;**但用户不知道你按默认走了**,会以为你能力不够或漏了活。

#### 冷启动先建几份载体 —— **默认 2 份**

⛔ **不要照搬别的项目有几份**,也**不要为省事合成一份**。按 `process.md` §7.0 三轴量下来,冷启动的最低配是**两份**:

| 建哪份 | 装什么 | 凭哪根轴分开 |
|---|---|---|
| **参数件** | §3.0 定下来的那几项 | **只在换人 / 换机器 / 换载体时才变** |
| **档案件** | 当前基线 · 在途 · 踩坑 | **每出一版就变** |

**「变更频率」这一轴不同 → 必须分开**(§7.0:三轴全同才许合,任一轴不同就不许合)。再往下的拆分(在途件 / 校验台账 / 反馈件…)**等频率或写入方真的分化了再做**。

**两份的最小骨架**(够用就行,别一上来就搭架子):

```
# {项目名} · 总览          ← 档案件
## 当前基线      ← 各资产版本号,唯一真值位置
## 在途          ← 还没完的事(条目多到每天都在动时,再按 §7.0 拆成独立在途件)
## 踩坑          ← 出过的事 + 改法

# {项目名} · 协作参数      ← 参数件(另一份文件)
## 参数表        ← §3.0 那几项,每项写「值 / 怎么定的 / 定于哪天」
```

**§3.0 问出来的答案记在参数件里**,并在档案件开头一行指向它。
> **为什么默认分开**:拿 `process.md` §7.0 的三轴量一下就知道——参数**只在换人 / 换机器 / 换载体时才变**,而档案件里的「当前基线」**每出一版就变**。合在一份里,**慢的那半会被快的那半拖着整篇重写**,正是台账涨到 40KB 的同一个机制。
> ⛔ **实测(2026-11-09 冷启动)**:v10.0 本节**一边写「默认 1 份」、一边写「默认分开」**,同一节里自相矛盾;测试窗口照「1 份」建,那一份「越写越长,每次改都要整篇读回来再整篇写」——**正好被它自己预言的那个机制打中**。v10.1 统一为 2 份。
> **只有一种情况可以并进档案件**:参数极少、档案件本身也小,且**两者都由同一方维护**(三轴全同 → 该合并)。

**活动件按角色称呼**(各人书名不同,包内只用角色名;实际书名填在参数里):

| 角色名 | 装什么 |
|---|---|
| **档案件** | 背景 · 目标 · 里程碑 · 当前基线(版本号)· 踩坑 · 已否决 |
| **校验台账** | 各已签发包的校验值与核验状态(§7.4) |
| **在途件** | 轮 / 天级:在途待办、发布面现状与口径(§7.0 / §7.4) |
| **站点版本真值表** | 站点各处版本戳的真值与处数 |
| **验证反馈件** | **任何验证方**照 skill 亲手做东西时检查出的 **skill 待修项**(总则2 第二层情况2)。站点验证、用 skill 还原设计稿、别的窗口照 skill 产出——**都落这一份,按来源分节,不另开文件** |
| **改包建议件** | 攒给本包签发方的改动建议 |
| **参数件** | §3.0 问来的那组参数值(设计真值来源 · 权威副本位置 · 路径 · 版本线与签发方 · 发布面有无 · 协作形态 · 各角色的实际书名) |

> ⛔ **这是七个角色,不是「必须七个文件」。** 哪几个角色合在一份里、哪几个必须分开,**拿 `process.md` §7.0 的三轴去量**(变更频率 · 写入方 · 读取时机):**三轴全同的必须合并,任一轴不同的必须分开**。
> **一个角色的落点空了也别删那份文件**(清空留壳,理由见 §7.0)——删了下次就有人另起新文件。

**一条发现该往哪份放 —— 看「要改的是谁」**(三份最容易混):

| 要改的是 | 放哪 |
|---|---|
| **被维护的那个 skill**(规则缺数值、两处矛盾、参考实现摘出来失效…) | **验证反馈件** |
| **本工作流包的规则**(过程、分工、载体、自检…) | **改包建议件**(§1:非签发方只提建议、不自行改包) |
| 都不用改,只是**这件事还没做完** | **在途件** |

> ⛔ **一条发现同时要改两边,就两份都记一条,别挑一份写。** 这与总则2「允许两边都要改」同源——**只写一份的那次,另一边那个洞就留在原地了**。

> **为什么要这么做**:本包后期会**发给别人一起用**,每个人的 agent、习惯、软件版本都不一样,而且软件还在迭代。**写死任何一处,换个人就得改包;问一次并记在项目侧,换人只改项目侧。**

#### 包分两层:**通用层** 与 **项目实例层**

⛔ **不要把整包都参数化**——过程规则抽成参数就只剩骨架,没人照着做得出东西。本包的分法是:

| 层 | 是什么 | 换个项目 / 换个人怎么办 |
|---|---|---|
| **通用层** | 过程规则本身:两次确认、签发唯一、不重复原则、三分支、活动件机制、输出前自检、载体按频率分…… | **原样照用**,只把参数(§3.0 问来的那组)换掉 |
| **项目实例层** | 带着具体工具名、仓名、域名、路径、字体、业务域、受控词表的那些节 | **整节替换**。通用的是「**要有这么一节**」,不是里面的值 |

**哪些节属实例层**:**节首都有 🏷️ 横幅**,读到就知道。⛔ **这里不再列一份清单**——清单和横幅是同一份信息的两处,必漂(§7.1)。

> **判法和 §7.1 升版测试同源**:**这条内容变了,要升的是本包的版,还是只是项目侧换了个值?** 只是换值 → 实例层。
> ⚠️ **实例层的每条结论都有保质期**(容器能力、字体可加载性、仓名、域名都会变)——引用时连同它的测定日期一起看,别当长期事实。同类坑:包里曾把「本容器缺 rsync」写成长期事实,几天后就不成立了。

### 3.1 这套东西由谁干 —— 默认只有「本窗口」

⛔ **本包不预设「谁判断、谁动手」的角色划分。判断与执行都在当前窗口;能自己做的一律自己做。**

> **v7.0 删除了【主线-大脑】(判断 / 裁决)与【主线-手】(文件执行)这对角色。** 当初分它们,是因为签发窗口的载体碰不到文件;现在多数载体自己就能读写文件、跑脚本、打包,**为一次机械操作去派活是纯浪费**。**旧包里凡写「一律交主线-手」「主线-大脑无本地访问能力」的条款一律作废**,按下面 §3.3 三分支现场判。

剩下的分工不是角色,是**能力槽位**——同一个窗口通常占满全部:

- **判断与固化**:取舍、结构设计、措辞;把 Figma 直读来的"样式数值"赋予语义与规则、固化进 skill;校验与裁决。**它维护的是 skill 这个执行载体,不是设计真值本身**(总则1)。
- **确定性执行(原「Code」槽位)**:抽取 token、零误差生成 css / md、一致性校验、渲染校验图、与设计图叠加比对、打包;文件建 / 移 / 改名 / 解压 / 归档、跑校验脚本。**本窗口做得到就自己做**(§3.3)。
- **Figma 读取(经 MCP 直读)**:`get_metadata` 节点结构、`get_design_context` 设计上下文、`get_variable_defs` 变量 / 语义 token 绑定。直读值即实测值,且能拿到变量语义 token 绑定(免去 hex 撞库猜测)。
  > 备用:外部提取模型(trae)是 MCP 不可用时的回退;启用时仍守「仅提数值、不碰规则语义、推导拒收」。
- **Design / 站点(可视化)**:把定稿内容画成对外展示页。**它就是另一个窗口,没有特殊性**——要它做事走 §3.3 分支③,和别的外援一样。
  > ⭐ **它有第二个身份:skill 的验证器。** 站点是**照 skill 亲手做组件、把规则展示出来**的地方,因此它会**成批撞出 skill 的洞**(规则缺数值、状态没说清、参考实现摘出来就失效、两处自相矛盾)。这类发现**要回流改 skill**,判据见 §2 总则2 第二层情况2;收集位置是包外**验证反馈件**。
  > ⭐ **不只站点**:**任何照 skill 亲手做东西的活动都是验证器**——用 skill 还原设计稿、别的窗口照 skill 出页面,撞出的洞**落在同一份验证反馈件里,按来源分节,不另开文件**。
  > **一个窗口做还是分窗口做,由用户定**:**同一个窗口里做完 skill 顺手做站,连提示词都不用写**;**分窗口做才需要一份转接件**(定稿参考实现文件 + 差异说明复制框,`process.md` §5.4)。**别把转接件当必经步骤**——它只是跨窗口时的搬运工具。

一句话:**设计真值在 Figma;直读 Figma 并把它固化成 skill,规则与裁决在本窗口;碰不到的事按 §3.3 三分支处理;站点既是对外橱窗、又是 skill 的验证器,它照 skill 做不出来的地方回头改 skill。skill 是站的上游,不是 Figma 的上游。**

> ⛔ **唯一没跟着删的「权」:签发权仍然只有一份。** 本包的版本由用户指定的单一窗口签发(当前【工作流窗口】),DS skill 的版本由 DS 线的签发窗口签。**这跟「谁动手」是两件事**——删的是动手分工,**不是签发唯一**。实证:2026-09-23 曾出现 v6.2 与 v6.3 两条基线并存,险些把 v6.3 静默回退。详见 `multi-window.md` §1。
> 开窗方式、以及多个窗口并行时怎么不互相踩 → `multi-window.md`。

### 3.2 轮次编号制 —— 凡有下游执行者,每轮一个唯一编号

格式 `EXEC-{窗口码}-{三位序号}`(例 `EXEC-WF-001`);**窗口码绑任务域、不绑窗口实例**,**每个域一条独立序列、不共享计数器**。

> **规则正文(格式、三条配套、文件名约定、为什么不用共享计数器)→ `multi-window.md` §9。**
> **出卡时照 `assets/templates/exec-card.md`,并同轮附转交复制框**(总则6)——只给 md 不算交付完。
### 3.3 碰本地的事怎么办 —— 三分支(硬约束)

**默认:当前窗口就是唯一窗口,自己能做的自己做。** 涉及**本地操作**(读写用户电脑上的工作区、跑本地脚本、归档改名、以及任何够不到的外部动作)时,先问一句「**本窗口到底够不够得到?**」,再走三条分支之一:

| | 情形 | 怎么做 |
|---|---|---|
| **①** | **不确定能不能做** | **自测一次,或问用户,两者都行。** 自测优先——一条只读命令就能定(列目录、读一个文件、`--dry-run`),比问一轮快。⛔ **不许跳过这一步直接假设**,往哪边假设都算违规。 |
| **②** | **确定能做** | **直接做。不出任务卡、不问。** 做完把「动了哪些文件、落在哪、验证结果」写清(见下三条底线)。 |
| **③** | **确定做不了** | 既不许假装能做,也不许停在这儿。给用户两条路、并说清各自代价:**(a) 推荐他自己操作**——给**确切路径 + 确切动作**,能一步到位就不要写成多步;**(b) 问他有没有别的能碰本地的 agent**——有,就给**任务卡 + 转交提示词**(任务卡骨架 `assets/templates/exec-card.md`;提示词直接把 `references/execution-standard.md` 整份给它)。 |

> **①的「自测」怎么算够**:跑**只读**命令看它到底成不成,并且**把错误原文读完**。`403` 可能是「这个仓没挂进本会话的授权集」而不是「环境不允许」,两者处置完全不同(实证见 `process.md` §4.9)。**把失败归因成环境墙,就等于把一条本来走得通的路关掉了。**
> **②和③的判据是能力,不是角色。** 能力随**窗口与载体**变,同一个人换个窗口答案就不一样——所以**每轮现场判,不照任何一张表派活**。
> **⚠️ 能力也可能比你以为的少**:某些载体能读写**自己的工作区**,却够不到**用户本地的工作区**。动手前先确认这一轮要碰的是哪一个;**够不到就如实说,不要假装。**

**⛔ 走②自己做时,原先靠任务卡保证的三件事一件都不能少**:

1. **不可逆操作先声明确切目标**(删除、覆盖、改名、推远端),并取得用户同意;
2. **留证**——改了哪些文件、验证结果当轮写清,**不只报「已完成」**;
3. **签发纪律照旧**:总则3.1 给内容指纹、总则4 确认后才打包、当轮登记**校验台账**。

> **实证**:DS v4.0.2 / v4.0.3 / v4.1.0 / v4.1.1 四版全由签发窗口直接改、直接出包,而当时规则里没有这种载体的位置,每轮都要临时判断。v7.0 把它定为**默认**。
> **反向实证**:`EXEC-DS-009`(2026-11-05)整张卡的主要内容是把几个文件夹挪进 `历史文件/`——**为一次 `mv` 走了一整轮出卡、转交、反馈**。按本节,那一轮该先走①自测,再按结果走②或③。

**通道现状**(事实记录,不是派活表;变了当轮改):

| 通道 | 通 / 断 | 走法 |
|---|---|---|
| Figma → 本窗口(MCP 直读) | 通 | 经连接器直读节点 / 变量,无需中转 |
| Figma → 本窗口(截图 / PDF / SVG / 文字) | 通 | 用户导出上传 |
| 本窗口 → 用户(md / css / zip / html) | 通 | present,用户下载 |
| 用户 → Design(提示词) | 通 | 粘贴 |
| Design → 本窗口(html / zip) | 通 | 用户导出上传,可解析 |
| 本窗口 ↔ **自己的**工作目录 | 通 | 直接读写,**确定性操作自己做** |
| 本窗口 ↔ **用户本机**工作区 | **看载体** | 有本机通道 → 通,自己做;**没有 → 走分支③** |
| 本窗口 ↔ 外网 / 发布仓写权限 | **看会话** | 先按①自测;403 先看是不是未授权而非被禁 |

设计目标:**让用户搬运次数最少、每次搬的东西最明确;自己做得到的绝不让用户做。**

### 3.4 全链路一句话

**构思 / 取值 → 固化 → 展示 → 对账取证 → 发布部署**,五段。**展开(每段产出什么、读哪节)→ `process.md` §3**,那里和九步标准循环放在一处,不在本页重画。

> **贯穿五段的铁律**:设计真值在 `{设计真值来源}`、skill 是固化而来的执行载体(总则1);差异**分两层裁决**,第二层**双向、逐条判、不套公式**(总则2);版本号全员贯穿(总则3);用户两次确认才算完成(总则4)。

## §5 用户每轮只需的动作

- 发 Figma 节点链接给 Chat(新维度 / 组件;截图作补充);
- 看 HTML / 预览,回一句确认或指出问题;
- 把 Chat 给的提示词 / 参考实现文件给 Design;
- (偶尔)对账时把 Design 导出拖进 Chat。

> **消耗用户点数的下游动作(Design 整站导出、Figma 写操作、部署上线)时机由用户主动提出**,本窗口不主动提议、不催。
